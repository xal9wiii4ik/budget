# QA Web Checklist: goal-planner (apps/web)

Источники решений: `.tasks/goal-planner/task.md`, `.tasks/goal-planner/architecture.md`
(§5 переход ручная→снизу, §6 напоминания, §7 вложения, §10 решения), `docs/web.md`.

## Scope

Только то, что навязывает или рисует браузер: дерево пунктов на экране цели,
три РАЗДЕЛЬНЫЕ величины прогресса, предупреждения (переход на счёт снизу,
превышение потолка, удаление файлов), инвалидация кеша после мутации,
блок ближайших сроков на главной, i18n, клавиатура/фокус, 375px.

**Не покрываем здесь (уже доказано дешевле):**
- коды 404/422 (`GOAL_ITEM_CYCLE`, `GOAL_ITEM_EXPENSE_ONLY`, `GOAL_ARCHIVED`,
  лимиты глубины/500/10 файлов), скоупинг по user_id, no-oracle, PATCH-семантика
  omit/value/null, окно `?days=` — pytest бэкенда + чеклист qa-engineer;
- рекурсивные агрегаты, remind-математика, effective target, `remaining_to_find` —
  юнит-тесты `domain/goal_plan.py`;
- сборка дерева из плоского списка, порядок сиблингов, форматирование денег/дат —
  vitest frontend-engineer (pure-модули рядом с фичей, как `realism.ts`).
- **Один браузерный вызов на новый роутер** (`/goals/{id}/items`, `/goals/upcoming`,
  files) обязателен — CORS/preflight curl'ом не ловится (урок 2026-08-18). Покрыт
  внутри TC-1/TC-5/TC-6, отдельным сценарием не заводим.

Подготовка данных — ВСЕГДА curl (цель, счёт, категории, транзакции, при
необходимости готовое дерево). Кликами формы фикстуры не создаём.
QA-пользователи: только `qa-*@budgetqa.dev`. Логин один раз на прогон,
токен переиспользуется во всех TC.

## Test cases

### TC-1: дерево «поездка → жильё → отель», три величины и «план неполный» — **live**
- **Precondition**: `qa-goalplan@budgetqa.dev`, цель «Поездка» (валюта цели = базовой),
  создана curl'ом БЕЗ пунктов; есть один счёт и категория расхода.
- **Steps**:
  1. Открыть `/goals`, войти в цель «Поездка».
  2. Добавить корневой пункт «Жильё» (без своей суммы), внутри него — «Отель в
     Кракове» с суммой; затем внутри «Поездки» — второй корень «Билеты» с суммой.
  3. Прочитать блок прогресса цели и строки дерева.
  4. Добавить ещё один лист («Страховка») и снова прочитать итоговую стоимость.
- **Expected**:
  - прогресс показан ТРЕМЯ отдельными величинами — «оплачено», «накоплено»,
    «осталось найти»; нигде нет одного числа, склеивающего оплачено+накоплено;
  - у цели видна подпись, что план неполный и итоговая стоимость собирается снизу
    и будет расти (task.md §«Деньги» — следствие, обязанное быть видно);
  - «Жильё» показывает рабочее число = сумма детей, а не собственную сумму;
  - после добавления «Страховки» итоговая выросла БЕЗ перезагрузки страницы
    (инвалидация `['goals', …]` + дерева), значение соответствует ответу сервера;
  - деньги отрисованы shared-хелпером (`formatMoney` с `locale`), без хвостов вида
    `12.500000001`, символ валюты цели.
  - Console: 0 ошибок; Network: дерево читается ОДНИМ запросом на мутацию-инвалидацию,
    без N+1 по узлам и без шторма перерендера.
- **Also here**: F5 на экране цели и прямой вход по URL цели — дерево восстанавливается
  раскрытым/консистентным, не редиректит и не падает.
- **Status**: ⏸ blocked (прогон 1) → ✅ pass (прогон 2, 2026-08-26)

### TC-2: первый пункт у существующей цели — явное предупреждение о переходе — **live**
- **Precondition**: цель «Ноутбук» с ручной суммой и БЕЗ пунктов (создана curl'ом,
  как сегодняшние цели после миграции 0011).
- **Steps**:
  1. Открыть цель — убедиться, что сумма ручная, поведение как сейчас (нет блока
     «план неполный», нет дерева).
  2. Добавить первый пункт.
  3. Подтвердить/отменить в предупреждении; если отменить — повторить и подтвердить.
  4. Задать «итоговую стоимость» руками (`final_cost_override`) и сравнить с суммой
     пунктов.
- **Expected**: ДО записи показано явное предупреждение, что итоговая стоимость
  начнёт считаться снизу из пунктов; отмена не создаёт пункт; после подтверждения
  карточка цели и `/goals` показывают новый режим без перезагрузки; при ручной
  итоговой расхождение с суммой пунктов показано честно (оба числа видны, одно не
  подменяет другое).
- **Status**: ⏸ blocked (прогон 1) → ✅ pass (прогон 2, 2026-08-26)

### TC-3: превышение потолка узла — предупреждение, НЕ блокировка — **live**
- **Precondition**: дерево из TC-1; у «Жилья» задана своя сумма (потолок) меньше
  суммы детей — доводится curl'ом.
- **Steps**:
  1. Открыть цель, найти «Жильё».
  2. Добавить/увеличить ребёнка так, чтобы сумма детей превысила потолок.
  3. Сохранить.
- **Expected**: сохранение ПРОХОДИТ (`ceiling_exceeded` — поле ответа, не ошибка);
  на узле видно предупреждение о превышении потолка с обеими величинами; кнопка
  сохранения не задизейблена, форма не показывает предупреждение как ошибку поля;
  наверх ушла сумма детей, не потолок; итоговая цели пересчиталась на экране.
- **Status**: ⏸ blocked (прогон 1) → ✅ pass (прогон 2, 2026-08-26)

### TC-4: привязка операции к пункту и перевязка на другой узел — **live**
- **Precondition**: дерево TC-1; операции создаются через форму транзакции
  (проверяем именно UI-канал привязки), исходное «оплачено» зафиксировано.
- **Steps**:
  1. `/transactions` → «Добавить», kind = расход, выбрать цель/пункт «Отель в
     Кракове», сумма 300, сохранить.
  2. Вернуться на экран цели — прочитать «оплачено» у «Отеля», у «Жилья» и у цели.
  3. Открыть операцию, перевязать её на «Билеты», сохранить.
  4. Снова прочитать все три уровня.
  5. Снять привязку (очистить поле) и прочитать ещё раз.
- **Expected**: после (1) «оплачено» выросло на трёх уровнях (узел → родитель →
  цель) БЕЗ перезагрузки; после (3) сумма НЕ задвоилась — у «Отеля» вернулось
  прежнее значение, у «Билетов» выросло, у цели осталось тем же; после (5)
  «оплачено» вернулось к исходному, сама операция осталась в списке;
  «осталось найти» пересчитано сервером и меняется согласованно;
  селектор пункта в форме недоступен/очищается для kind = income и transfer
  (пользователь не может создать заведомо 422).
- **Status**: ⏸ blocked (прогон 1) → ✅ pass (прогон 2, 2026-08-26)

### TC-5: удаление узла с фото — ConfirmDialog называет количество файлов — **deferred**
- **Precondition**: у «Отеля» 2 фото загружены и подтверждены (curl: create →
  presigned PUT → confirm), у «Жилья» — 1 фото; к «Отелю» привязана операция.
- **Steps**:
  1. Открыть цель, посмотреть превью вложений у «Отеля» (`view_url` минтится
     только для `uploaded`).
  2. Нажать удаление на «Жилье» (узел с поддеревом).
  3. Прочитать текст ConfirmDialog, отменить, затем повторить и подтвердить.
- **Expected**: диалог называет КОЛИЧЕСТВО файлов, которые уйдут вместе с
  поддеревом (`files_count` по поддереву), и предупреждает про дочерние пункты;
  отмена ничего не удаляет; после подтверждения поддерево исчезло с экрана без
  перезагрузки, итоговая стоимость и «оплачено» пересчитались, а САМА операция
  осталась в `/transactions` — просто без привязки; число «N файлов» склоняется
  правильно в ru (Intl.PluralRules, ловушка 21 vs 11); битая/непрогруженная
  картинка не роняет экран.
- **Status**: ⏸ blocked (прогон 1) → ❌ fail (прогон 2, 2026-08-26) — см. F-1 и F-2

### TC-6: напоминание «за N дней», блок ближайших сроков, перенос дедлайна цели — **deferred**
- **Precondition**: цель с дедлайном; пункт БЕЗ своего срока (наследует) и пункт со
  своим сроком в ближайшие 30 дней.
- **Steps**:
  1. В форме пункта выбрать «за N дней», ввести N — прочитать подсказку с датой.
  2. Переключить на «конкретную дату» и обратно; сохранить «за N дней».
  3. Открыть `/transactions` (или главную с виджетами) — найти блок ближайших
     сроков рядом с `UpcomingCharges`.
  4. Перенести дедлайн ЦЕЛИ на месяц вперёд, вернуться к пункту и к блоку.
  5. Переключить язык ru ↔ en в настройках и перечитать экран цели и блок сроков.
- **Expected**: форма СРАЗУ показывает получившуюся дату напоминания и она едет за
  сроком; выбор — ровно один из двух вариантов (второе поле очищается, не бывает
  обоих сразу); пункт без своего срока подписан как унаследованный («к 15 июня,
  срок цели») и после (4) его дата и дата напоминания сдвинулись, а пункт с
  конкретной датой напоминания остался на месте; блок ближайших сроков обновился
  без перезагрузки; архивная цель из блока исчезает; при ru↔en переводится вся
  служебная копия (заголовки, подписи «срок цели», «план неполный», предупреждения),
  а имена цели и пунктов НЕ переводятся, даты и суммы — в локали языка.
- **Status**: ⏸ blocked (прогон 1) → ✅ pass (прогон 2, 2026-08-26)

## Сквозные проверки (выполняются ВНУТРИ сценариев, не отдельными прогонами)

- **Console/Network**: в каждом live-TC — ноль console-ошибок, нет дублей и штормов
  запросов, нет 4xx от собственных действий UI.
- **Состояния экрана**: 4 арма `queryPhase` на экране цели и в блоке сроков —
  loading (скелетон, не вечный), unreachable (сетевой алерт, не бесконечный
  скелетон), error (восстановимая, не белый экран), empty (цель без пунктов —
  подсказка, что делать). Проверяется в TC-1 и TC-2.
- **375px**: TC-1 и TC-4 повторить на мобильной ширине — дерево с отступами не
  переполняет экран, кнопки «вверх/вниз» и удаление достижимы, модалка формы
  пункта скроллится, суммы не обрезаются. Скриншот — один на экран, проверяет всё
  видимое сразу.
- **Клавиатура/фокус/a11y**: TC-2 и TC-4 пройти только с клавиатуры (Tab/Enter):
  поля пункта имеют лейблы, ConfirmDialog ловит фокус и возвращает его на кнопку
  после закрытия, дизейбл кнопки во время мутации не даёт двойного сабмита
  (двойной Enter не создаёт два пункта / две привязки).
- **Dirty-guard**: закрытие формы пункта с изменениями — подтверждение; чистая
  форма закрывается молча; во время in-flight мутации подтверждения нет
  (`shouldConfirmDiscard`).

## Блокер прогона 2026-08-26 (web-qa)

Живой прогон TC-1…TC-6 НЕ выполнен: выданный стенд не позволяет браузеру
обратиться к API скоупа.

Улики:
- web (vite :5199) собран с `VITE_API_URL=http://localhost:8011` (process env
  процесса vite, поднят до этого прогона). `apps/web/src/lib/api.ts` берёт
  `import.meta.env.VITE_API_URL` — значение фиксируется при старте vite.
- API :8011 — СТАРЫЙ код без goal-planner: в его `openapi.json` нет
  `/goals/{goal_id}/items` и `/goals/upcoming`; логин `qa-goalplan-a@budgetqa.dev`
  → `LOGIN_BAD_CREDENTIALS` (другая БД).
- API :8012 (нужный, БД `budget_qa_final`) отвечает на preflight с origin
  `http://localhost:5199`: `400 Disallowed CORS origin`. Дефолт
  `Settings.cors_origins = ["http://localhost:5173"]`, переменной `CORS_ORIGINS`
  у процесса нет.
- Браузер на форме логина: console `blocked by CORS policy: No
  'Access-Control-Allow-Origin' header`, network `POST http://localhost:8011/auth/login
  [FAILED: net::ERR_FAILED]`.

Починка (нужен рестарт, у web-qa нет прав поднимать/гасить процессы):
API `:8012` c `CORS_ORIGINS='["http://localhost:5199"]'` (остальной env тот же:
`DATABASE_URL=…/budget_qa_final`, `JWT_SECRET=qa-final-secret-key-goalplanner`,
шедулеры off) и vite `:5199` c `VITE_API_URL=http://localhost:8012`.

### Что успело подтвердиться до блокера (curl, БД `budget_qa_final`)

Фикстуры оставлены в стенде для повторного прогона (пользователь
`qa-goalplan-a@budgetqa.dev`): счёт `QA Карта RUB`, цель `Поездка в Краков`
(RUB, дедлайн 2026-11-15, БЕЗ пунктов — под TC-1), цель `Ноутбук` (ручная сумма,
без пунктов — под TC-2), цель `Поездка (проверка сумм)` с деревом под арифметику.

Арифметика трёх величин сошлась с ручным расчётом (это API-уровень, экранная
проверка пункта заказчика №1 остаётся невыполненной):
Отель 45 000 RUB (в «Жильё») + Билеты 30 000 RUB + Экскурсии 200 EUR
(курса на стенде нет → `converted_minor: null`, `planned_unconverted_count: 1`;
после ручного `converted_minor = 20 000 RUB` счётчик несконвертированного = 0)
→ `planned_total_minor = 9 500 000` (95 000 RUB), взнос 15 000 RUB
→ `saved_minor = 1 500 000`, привязанная трата 300 RUB → `paid_minor = 30 000`
на трёх уровнях (Отель / Жильё / цель — БЕЗ задвоения),
`remaining_to_find_minor = 7 970 000` = 9 500 000 − 30 000 − 1 500 000. ✅
`effective_deadline` пункта без срока = дедлайн цели, `deadline_inherited: true`.
`GET /goals/upcoming?days=90` отдаёт `goal_name`, `breadcrumb`, `goal_currency`,
`deadline_inherited` — данные для блока сроков есть.

MinIO: под префиксом пользователя `ec4bd702-…` объектов НЕТ (list-objects-v2,
`KeyCount = 0`) — этот прогон файлов не создавал, файлы прошлой подготовки
уже унесены каскадом.

### Находки

**F-1 (functional, major для TC-5): в вебе вообще нет клиента файлов пункта.**
`apps/web/src/features/goals/plan/PlanNodeDetails.tsx` рисует только СЧЁТЧИК
(`item.files_count`), а в его же докстринге написано: «W1 shows the file COUNT
only; the attachments themselves (presign → PUT → confirm → `view_url`) arrive
with the files endpoints». Поиск по `apps/web/src` не находит ни одного
обращения к `/goals/{goal_id}/items/{item_id}/files`, ни одного использования
`view_url`, ни UI загрузки. Улика из браузера: раскрытие «Подробности» у «Отеля»
с тремя файлами (2 uploaded + 1 pending) не порождает НИ ОДНОГО запроса к
files-роутеру (`read_network_requests` по шаблону `files` — пусто), на экране
только текст «3 файла». Следствие: пункт TC-5 «превью `view_url` только для
uploaded» непроверяем — фичи в вебе нет. При этом `docs/web.md` §«Goal plan
screen» утверждает обратное: «details `PlanNodeDetails` (links, attachments via
files GET — `view_url` only for uploaded)» — дока опережает код.

**F-2 (functional, minor, но вводит в заблуждение перед необратимым действием):
ConfirmDialog удаления считает узлы включая сам удаляемый.**
`routes/GoalPlanPage.tsx` передаёт `subtreeSize(deleteNode)` (а `subtreeSize` в
`buildTree.ts` = 1 + дети) в строку `goalPlan.deleteMessage`: «Удалить «{name}»?
Вместе с ним уйдут {items} и {files}…». Улики с экрана:
- удаление ЛИСТА «Билеты» (детей нет): «Удалить «Билеты»? Вместе с ним уйдут
  **1 пункт плана** и **0 прикреплённых файлов**.» — «вместе с ним» + «1 пункт»
  сообщает о несуществующем дополнительном пункте, и клауза про файлы печатает
  ноль вместо того, чтобы исчезнуть;
- удаление «Жилья» с ОДНИМ ребёнком: «уйдут **2 пункта плана**» — тоже на один
  больше, чем реально уйдёт «вместе с ним».
Плюс согласование: «уйдут 1 пункт» (нужно «уйдёт»).

**F-3 (minor, UX/копия): после перехода в режим «снизу» заданная сумма цели
пропадает с экрана.** Диалог обещает: «Заданная вами сумма останется
