## Решения по четырём переданным вопросам (архитектор, приняты)

a. **Глубина/фото**: лимиты валидацией (константы config, не БД — «динамичная БД»
   соблюдена): глубина ≤ 6, пунктов на цель ≤ 500, фото ≤ 10/пункт по 5 МБ.
   Гонка на лимите 500 — обычная проверка, без блокировки (решение PM: защита
   интерфейса, не денежный инвариант; контраст с «одна операция — один узел» записан).
b. **Порядок**: `sort_order` шаг 1024, но перестановка — СЕРВЕРНАЯ операция
   PATCH `{"move":"up"|"down"}` (решение PM: атомарность, зазор — забота сервера);
   DnD в v1 не делаем, схема готова.
c. **Статус пункта**: в v1 нет — «оплачено» выводится из денег, второй источник
   правды не заводим (YAGNI).
d. **Архивация**: пункты/файлы/привязки сохраняются; записи → 422 GOAL_ARCHIVED
   (404 раньше archived, no-oracle); из upcoming/главной архивная цель исчезает;
   разархивация возвращает всё.

## Риски

1. **Задвоение оплаты** — форма данных (колонка + CHECK expense-only); тест PATCH kind
   у привязанной строки обязателен (qa A1).
2. **Циклы/конкурентность** — триггер + advisory lock; только живой Postgres докажет (A3).
3. **Регресс существующих целей** — effective_target меняет ladder-математику для ВСЕХ
   целей; без пунктов число обязано остаться байт-в-байт (plan.md тест 11).
4. **Контракт в 3 подзадачах** — каждый мерж пары гоняет тесты четырёх потребителей
   (политика 2026-08-23; drift-тест mcp-server — именно тот сторож, что краснел 08-23).
5. **Best-effort удаление MinIO** — осиротевшие объекты = утечка диска, не данных;
   лог ошибок обязателен.
6. **Живая конвертация «оплачено»** (третья арма bucket-порядка) — число может дрейфовать
   с курсами; принято PM вместе с Д1.
7. **Инвалидация после привязки операции** — главный веб-риск: tx-мутации должны трогать
   `['goals', goalId, 'items']` и `['goals','upcoming']`, иначе «оплачено» врёт до F5 (TC-4).
