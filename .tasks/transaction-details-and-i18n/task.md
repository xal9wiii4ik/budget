# Scope: transaction-details-and-i18n

Семь замечаний пользователя после живой работы в приложении. Все проверены по коду
оркестратором (2026-08-22). Грумминг-only.

## Верифицированные факты (не перепроверять, ссылки точные)

- F1. Валюта операции штампуется от счёта; присланное несогласное значение → 422
  `ACCOUNT_CURRENCY_MISMATCH` (docs/backend.md /transactions). В веб-форме валюта —
  read-only тег у поля Amount (TransactionFormModal.tsx ~581); легенда
  «Amount in {baseCurrency}» (~597) — секция конвертации в БАЗОВУЮ валюту профиля
  (у пользователя RUB), он принял её за валюту операции.
- F2. Profile: только `base_currency` (default 'RUB') + `monthly_income_minor`
  (models/profile.py). Ни country, ни language нет нигде.
- F3. AI-гейт — только внутри POST /receipts/{id}/parse (routers/receipts.py:261).
  Presign POST /receipts и GET /receipts/{id} НЕ гейтятся. Привязка receipt_id при
  создании tx не требует статуса — pending/failed можно линковать (routers/
  transactions.py:249-262, D8). НО receipt_id create-only: в TransactionUpdate его
  нет («re-linking is not a feature», schemas/transaction.py:195).
- F4. В tx-форме `note` есть всегда (textarea, ~733), `merchant` — только в
  confirm-режиме чека. merchant→category map учится на CREATE при
  merchant+category_id (transactions.py:640-657, D7); PATCH не учит (:995).
  В строке списка note — вторичный текст (TransactionRow.tsx:94).
- F5. 19 системных категорий в 0003 — русские имена, UUID ЗАМОРОЖЕНЫ (contract).
  Категории уходят клиентам полем `name` как есть. i18n-инфраструктуры нет вообще.
- F6. Ошибки API — строковые SCREAMING_SNAKE коды (conventions.md) — идеально под
  клиентскую локализацию.
- F7. Goal.priority: int|None, меньше=важнее, None→в конец (schemas/goal.py:65).
  UI это никак не объясняет.

## Подзадачи

### S1 — двусторонняя валютная модель операции + поля профиля (FULL: миграция+деньги+контракт)
Пользовательский сценарий: BYN-карта, трата 50 EUR в Европе, банк списал 165 BYN.
Сейчас непредставимо (F1).

РЕКОМЕНДУЕМАЯ модель (архитектору стресс-тестить, зеркало переводов):
- `amount_minor`+`currency` ОСТАЮТСЯ суммой списания в валюте счёта — вся существующая
  математика (балансы, base-snapshot, статы, лимиты, tx_totals) не трогается.
- НОВАЯ nullable-пара `original_amount_minor`+`original_currency` — «сколько потрачено»
  в валюте траты. NULL = валюта траты совпадает со счётом (сегодняшнее поведение,
  обратная совместимость: замороженная мобилка продолжает работать без изменений).
- Если original задан и валюта отличается: сервер считает сумму списания по дневному
  курсу (fx_lookup, nearest-previous), НО присланное пользователем `amount_minor`
  ПОБЕЖДАЕТ (банк даёт свой курс) — семантика как у base-snapshot override.
- CHECK'и: original-пара целиком или никак; original_currency != currency счёта
  (или разрешить равные? — архитектору решить); original_amount_minor > 0.
  Взаимодействие с kind=transfer — original запрещён на переводах (у них уже
  counter-пара).
- Отображение: показываем трату (original), списание — вторично. Курс — read-only
  производное как transfer_rate.
- Profile: + `country` (ISO-3166 alpha-2, nullable) + `language` ('ru'|'en',
  default?) в ТУ ЖЕ миграцию. Первый вход: подсказка из локали браузера/устройства,
  подтверждает пользователь. country → валюта по умолчанию для поля траты
  (маппинг страна→валюта в packages/shared).
- Лейбл основного поля суммы обязан называть валюту в любом исходе.

### S2 — страна траты на операции (STANDARD)
`transactions.country` (char(2), nullable), в «More options», дефолт из профиля
(проставляет клиент; MCP/PAT-создания без страны — ок, nullable). В статистику
СЕЙЧАС не заводим (задел; максимум — колонка в CSV-экспорте). Миграция едет
вместе с S1 (меньше границ).

### S3 — фото в форме операции (FULL: изменение контракта)
Переиспользование presign-flow БЕЗ распознавания (работает без ключа — F3):
POST /receipts → PUT в MinIO → receipt_id в create body (уже работает).
Контрактное изменение: разрешить `receipt_id` в PATCH (attach к существующей,
null→значение; detach значение→null — решить). Просмотр: presigned GET уже есть.
Веб: кнопка «прикрепить фото» в форме + миниатюра/просмотр при редактировании.

### S4 — «название» операции (FAST)
Новую колонку title НЕ заводим. Показываем `merchant` во ВСЕХ create/edit формах
с человеческим лейблом («Name / place»), note остаётся заметкой. Бонус: create с
merchant+category уже учит автокатегоризацию (F4). В строке списка merchant —
главный текст, note — вторичный. PATCH merchant уже в контракте — контракт не
меняется.

### S5 — i18n веба + перевод системных категорий (STANDARD, независимая линия)
- Минимальный i18n-слой (frontend выбирает: лёгкий словарный, без тяжёлых зависимостей
  без нужды), ru+en, весь UI веба.
- Системные категории: маппинг UUID→ключ перевода в packages/shared (19 замороженных
  UUID — F5), имя из API — fallback. Пользовательские категории НЕ переводятся.
- Ошибки: серверные коды остаются кодами, человеческий текст подбирает клиент (F6).
- Язык — в профиле (сервер, колонка из S1), до логина/оффлайн — локальный кеш.
- MCP/advisor продолжают видеть русские имена из API — принято, не трогаем.

### S6 — мобильная часть (ОТДЕЛЬНАЯ СТРОКА, мобилка заморожена)
S1 спроектирован обратно-совместимым — мобилка живёт без изменений. Отдельный
отложенный/параллельный пакет: original-пара в форме, страна, фото, лейблы, i18n.
Требует явного решения о разморозке. mobile-engineer даёт только оценку+тезисы.

### S7 — priority у целей (FAST)
API не меняем (int, меньше=важнее — F7). UI: рекомендация — селект
Высокий/Средний/Низкий → 1/2/3 при создании, существующие произвольные числа
показываются числом с подсказкой «1 = самый важный»; либо просто подпись+hint.
Frontend решает дешевле/понятнее, обосновать в плане.

## Порядок и параллель
S1 бэк — первым (контракт); S2, S3-бэк — в той же линии. Веб-подзадачи стартуют
сразу против контракт-скетча из этого файла. S5 — полностью независимая линия,
можно параллелить или откладывать. S4, S7 — косметика, любое окно.

## Ограничения
- Никаких правок docker-compose/.env/портов. Не коммитить (грумминг).
- openapi.json + schema.d.ts — одним коммитом при имплементации.
- Тесты — только на реально ломаемое поведение.

## Решения PM (2026-08-22, зафиксированы в ходе грумминга — ОБЯЗАТЕЛЬНЫ)

- PM-1. `profiles.language` — default NULL, НЕ 'ru'. NULL = «пользователь не выбирал»,
  клиент берёт язык устройства/браузера. Причина: бэкфилл-default навязал бы новый
  смысл замороженной мобилке; пустое поле честно говорит «выбора не было». Первый
  явный выбор пользователя записывает значение. Архитектору/бэку: никакого
  server_default в миграции.
- PM-2. Фото (S3): отвязка И перепривязка receipt_id РАЗРЕШЕНЫ обе. Файл в MinIO
  при отвязке НЕ удаляется — осиротевший объект остаётся, осознанный размен
  (диск дешевле безвозвратно удалённого чека). Уборка осиротевших объектов —
  отдельный follow-up с явной пометкой: только с подтверждением пользователя,
  никакой автоматической чистки по таймеру.
- PM-3. STOP-пробы скоупа: (a) живой дневной курс на реальных данных провайдера,
  (b) полный круг presigned URL → реальная загрузка в MinIO → привязка → чтение
  того же файла. Пауза на пробы — после закрытия S1 (конвертация) и S3 (привязка),
  ДО старта живой проверки веба.
- PM-4. Масштаб QA-среза: 25 сценариев, из них 6 живых — финальный. При
  финализации после ответов архитектора сценарии НЕ добирать.
