## Rulings on the backend plan's flags
- FLAG-1 (A1 wrong — `occurred_at` is a `Date`): ACCEPTED. A1 is rewritten in architecture.md;
  `account_balance_as_of` uses `occurred_at <= as_of`; the boundary test is "dated `period_to` IN,
  `period_to + 1 day` OUT".
- FLAG-2 (tail-less date line → `StatementParseError`): REJECTED. The whole reason for an LLM here
  is tolerance to a text layout the regex did not foresee. A line that starts with `dd.mm.yyyy ` but
  whose tail does not match still goes to the model; its deterministic `description` is the line
  minus the leading date (whitespace-collapsed). The self-check is what catches a misread. Lines
  after the table header that do NOT start with a date are CONTINUATIONS and are appended to the
  previous operation line with one space (pypdf wrapped it) — never dropped.
- FLAG-3 (`ContentPart` must carry `ToolUseBlock`): ACCEPTED as planned (widen the union, no new type).
- FLAG-4 (short opaque keys `r1/t1` in the reconcile prompt, uuids mapped back server-side): ACCEPTED.
- FLAG-5 (`max_tokens = max(1024, 150 × lines)`): ACCEPTED.
- FLAG-6 (server tail regex makes the model's numbers redundant per row): planned as written is
  ACCEPTED for v1 — the model is the extractor of record (date, amount, currency, original pair,
  merchant); the server's tail parse feeds `description` only, PLUS the free `tail_mismatch_rows=`
  count in the summary log line. Decision whether the per-row cross-check becomes a self-check is
  taken after the first LIVE run, with that number. Recorded as follow-up `alfa-row-crosscheck`.
- FLAG-7 (no column for the extraction prompt version): ACCEPTED — log line only.
- Open question "keep `tool_choice='any'`": keep.
- Fixture PDFs: 3 files, target ≤ 60 KB each (font subset dominates; 50 was a guess), generated by the
  manual script (A2). Content contract (from qa-checklist ask 1): `alfa_good.pdf` (2 pages, ≥ 24 ops,
  one FX row with a RUB original pair, one `Перевод` row, one `Зачисление` row whose description
  contains inner `dd.mm.yyyy` dates, one wrapped long description), `alfa_mismatch.pdf` (same
  shape, closing balance off by a known amount → `self_check_failed='balance'`),
  `alfa_llmfail.pdf` (one description containing `LLMFAIL`). All merchants/amounts/ids invented.

   description, merchant, amount_minor, currency, kind} | null`, `.transaction: {id, occurred_at,
   merchant, note, amount_minor, currency, kind} | null` (new small schemas `DiscrepancyRowView` /
   `DiscrepancyTxView`; the router fills them from the facts it already loaded, no extra query).

4. Never-reconciled → 200 `status:'none'`, `items: []`: CONFIRMED.
5. Language contract: the reconcile system prompt instructs the model to write `explanation` and
   `summary` in the language given in the data document — the router passes `profile.language`
   (`ru|en`, default `ru`). Same for nothing else (the extract prompt returns no prose).
6. `ai_available` on the session read: REJECTED in that form. INSTEAD `GET /statement-imports/formats`
   gains two additive fields: `ai_formats: string[]` (= `EXTRACTORS` keys) and `ai_available: bool`
   (= `app.state.llm is not None`). This replaces the web plan's frozen client-side `AI_FORMATS` set
   (decision 1 there is overruled: the server already owns the registry; a second copy on the client
   drifts) and gives the reconcile button a live gate (`ai_available`), not the stored `ai_status`.
   `['imports','formats']` is already cached 1h — the web may refetch it on the import page mount.
7. Sequencing: web part B after the contract regen — ACCEPTED (schedule below).
