# Verified facts: fastapi-users 15.0.5 (Phase 3.6 gate)

Verified by senior-lead on 2026-07-24 by installing the CURRENT release into a
scratch venv and reading its source (`inspect.getsource`), not from memory or
old docs. Resolved versions: `fastapi-users 15.0.5`,
`fastapi-users-db-sqlalchemy 7.0.0`, `pwdlib 0.3.0`, `pyjwt 2.13.0`,
`argon2-cffi 25.1.0`, `python-multipart 0.0.32`. All agents MUST plan against
these facts; if implementation resolves a different version, re-verify.

## F1. Routers fastapi-users actually ships (and their paths)

`fastapi_users.router` exports exactly: `get_auth_router` (POST `/login`,
POST `/logout` — per authentication backend), `get_register_router`
(POST `/register`), `get_reset_password_router` (POST `/forgot-password`,
POST `/reset-password`), `get_verify_router` (POST `/request-verify-token`,
POST `/verify`), `get_users_router` (GET/PATCH `/me`, GET/PATCH/DELETE `/{id}`).

**There is NO refresh endpoint anywhere in the library.** The architecture
doc's sentence "fastapi-users сразу даёт регистрацию, вход, refresh и сброс
пароля" is WRONG on "refresh". Refresh must be designed and built by us.

## F2. Login contract

The stock login route takes `OAuth2PasswordRequestForm = Depends()` —
i.e. `application/x-www-form-urlencoded` body with fields `username` (carries
the email) and `password`. NOT JSON. `python-multipart` is a hard dependency of
fastapi-users (auto-installed). Bad credentials / inactive user → 400 with
`{"detail": "LOGIN_BAD_CREDENTIALS"}`. Success response comes from the
transport: `BearerTransport` returns `BearerResponse` with EXACTLY
`{access_token, token_type}` — **no refresh_token field**. Returning an
access+refresh pair requires a custom transport or a custom login route.

## F3. Password hashing

`PasswordHelper` default (no config needed) = pwdlib `PasswordHash` with
`(Argon2Hasher(), BcryptHasher())` — argon2 for new hashes, bcrypt accepted
for verify-and-migrate. fastapi-users pins `pwdlib[argon2,bcrypt]==0.3.0`.
The architecture's "argon2 через pwdlib" is satisfied by the DEFAULT — zero
custom config.

## F4. Strategies

- `JWTStrategy(secret, lifetime_seconds, token_audience=["fastapi-users:auth"], algorithm="HS256")` — access token.
- `DatabaseStrategy(database: AccessTokenDatabase, lifetime_seconds)` — opaque
  token `secrets.token_urlsafe()` (43 chars) stored in a DB table;
  `read_token` enforces max age from `created_at`; `write_token` /
  `destroy_token` give create/revoke. **This is the natural DB-stored
  revocable refresh-token primitive.** Adapter:
  `SQLAlchemyAccessTokenDatabase(session, token_model_class)` — accepts ANY
  model class with `token` (pk), `created_at` (tz-aware), `user_id` columns.

## F5. Table mixins (fastapi-users-db-sqlalchemy 7.0.0) — friction points

- `SQLAlchemyBaseUserTable.__tablename__ = "user"` (architecture wants
  `users`); columns: email String(320) unique+index, hashed_password
  String(1024), is_active/is_superuser/is_verified booleans.
- `SQLAlchemyBaseAccessTokenTable.__tablename__ = "accesstoken"`; token
  String(43) PK; UUID variant hardcodes `ForeignKey("user.id", ondelete="cascade")` in a `declared_attr`.
- `SQLAlchemyBaseOAuthAccountTable.__tablename__ = "oauth_account"`; UUID
  variant also hardcodes `ForeignKey("user.id")`.
- All UUID mixins use the library's `GUID` TypeDecorator (not native
  `sqlalchemy.Uuid`) — it maps to native UUID on Postgres, but migrations
  autogenerated from it import `fastapi_users_db_sqlalchemy.generics.GUID`.
- `SQLAlchemyUserDatabase(session, User)` works with ANY model exposing the
  protocol columns — using the mixins is optional, not required.

## F6. The current-user dependency

`FastAPIUsers(get_user_manager, auth_backends).current_user` is an instance
attribute delegating to `Authenticator.current_user(optional/active/verified/superuser, get_enabled_backends)`.
`current_active_user = fastapi_users.current_user(active=True)`. Security
consequence: if the `FastAPIUsers` instance is constructed with ONLY the JWT
backend, opaque refresh tokens can NEVER authenticate a protected route (JWT
decode fails) — the refresh backend must not be registered on the
Authenticator used for protected endpoints.

## F7. UserManager hooks available

`on_after_register`, `on_after_login`, `on_after_forgot_password` (receives
the reset token — our delivery point since there is no email infra),
`on_after_reset_password`, `validate_password`, plus verify/update/delete
hooks. `email-validator` is a hard dep — register validates email shape.
