# plan-web.md — веб-подзадачи (тезисно)

## S1 `category-drilldown` (STANDARD, web-only, контракта не трогает)

- **/categories → /transactions**: на КАЖДОЙ строке категории (системной и
  пользовательской) — отдельный аффорданс «операции» (иконка-ссылка), ведущий на
  `/transactions?category=<id>` (месяц не проставляем → дефолт = текущий).
  НЕ вешать на весь ряд: у пользовательских строк клик уже занят редактированием,
  системные — намеренно неинтерактивны (C4); отдельная ссылка не ломает ни то, ни то.
- **TransactionsPage**: читать `?category=` по образцу `?account=` (UUID-валидация,
  мусор = нет фильтра), класть `category_id` в `TxListFilters` (omit при отсутствии —
  нефильтрованный ключ не меняется) и в ExportFilters (экспорт уже готов к этому).
- **Чип активного фильтра**: «Категория: <имя из categoryIndex>» + крестик-сброс
  (убирает URL-параметр). Имя из archived-inclusive кэша — архивная категория
  показывается честно, с бейджем.
- **Расширение диапазона**: MonthPicker уже листает месяцы; добавить переключатель
  «за всё время» (URL-флаг, напр. `?range=all`): из TxListFilters уходят from/to
  (сервер уже принимает оба опциональными — БЕЗ серверных изменений), SummaryHeader
  (месячный агрегат) скрывается, MonthPicker заменяется на кнопку возврата к месяцу.
  Кастомный date-range picker — НЕ делаем (отложено, см. open questions).
- Инвалидации не меняются: category_id — данные-в-ключе, предикат
  `key[0]==='transactions' && key[1]!=='summary'` уже накрывает такие ключи.
- i18n: все новые строки через dict.en/dict.ru.

Оценка: написание 15–20, гейты 5, верификация — в общем QA-прогоне (+таргет-проба).

## S2 `category-search` (FAST, web-only)

- Поле поиска над списком на /categories; чисто клиентский фильтр localState
  (НЕ URL — эфемерный, ничего не шарить), по подстроке без регистра:
  `name.toLocaleLowerCase(locale).includes(q.toLocaleLowerCase(locale))`.
- Фильтруются УЖЕ ПЕРЕВЕДЁННЫЕ имена (systemCategoryName применяется в select
  useCategories) — русский юзер ищет «Продукты», не "Groceries".
- Пустой результат — честная заглушка «ничего не найдено» + сброс.
- Групповая структура (expense/income, archived) сохраняется; пустые группы скрыть.
- Тест только на чистую функцию фильтра, если она выносится; DOM-тесты не писать.

Оценка: написание 10, гейты 3, верификация 5 (в общем прогоне).

## S3-web `tx-filters-search-sort` (часть FULL-подзадачи S3)

Может писаться параллельно бэку против контракта из plan.md (типы известны заранее).

- **Поиск**: инпут в шапке листа; debounce ~350мс; в `TxListFilters` кладётся
  триммленное значение (пустое = omit). URL-параметр `?q=` (шареемость, back).
- **Фильтры-минимум** (компактный popover «Фильтры», НЕ постоянная панель):
  категория (селект, тот же URL-параметр, что у S1 — ЕДИНЫЙ механизм, не второй),
  страна (опции из логики Intl.DisplayNames, вынести построение из
  TransactionFormModal в переиспользуемый модуль), сортировка (4 значения селектом,
  дефолт date_desc = omit). kind-фильтр НЕ добавляем (сценарии не требуют).
- Все значения — URL-параметры и данные-в-ключе TxListFilters; невалидные значения
  из URL = нет фильтра (паттерн `?account=`).
- Экспорт получает q/country (не sort). Счётчик активных фильтров на кнопке popover.
- amount-сортировка ломает группировку по дням (groupByDay): при sort≠date_* —
  плоский список без day-заголовков (решение зафиксировать; группировать по дням
  внутри amount-сортировки бессмысленно).
- Чистые модули (парсинг/сериализация фильтров из URL) — с node-vitest тестами.

Оценка: написание 20–25, гейты 5, верификация — общий QA-прогон скоупа.
