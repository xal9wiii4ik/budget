## Findings

1. **MAJOR** — `apps/api/src/budget_api/services/debt_writes.py:279-316` (`update_movement`). The row lock is taken (l.309) and the totals re-read under it (l.310), but the ceiling then uses `stored = row.debt_amount_minor` (l.311) from the `Transaction` object loaded BEFORE the lock (`load_own_repayment` in the router). SQLAlchemy does not expire identity-map objects on a Core `execute`, so under READ COMMITTED a concurrent edit of the SAME repayment that commits between the load and the lock makes `repaid_minor − stored + new` wrong by `(R_committed − R_stale)`. Concrete: principal 100, repayments R=50, S=40. A: R→5 (commits, repaid=45). B (loaded R=50 before A committed): R→70 — real check 45−5+70=110 > 100 must refuse; computed 45−50+70=65 passes → R=70, S=40, remaining = −10. This is the exact race the architecture's "lock → totals → refuse" sentence claims is impossible. The same staleness feeds `row.currency`/`row.amount_minor` into the "keep" branches (acceptable last-write-wins), but the ceiling is money. Minimal fix: move `await _lock(...)` to the top of `update_movement` and follow it with `await session.refresh(row)` (one SELECT), so `eff_*`, `_amounts` and `stored` all read post-lock state; nothing else changes. `add_repayment` is unaffected (it inserts, reads no stored row).

2. **MINOR** — `apps/api/src/budget_api/routers/debts.py:245-263 + 635-638` (`_replayed_debt_id` in `record_debt_repayment`). The replay hit is user-scoped (no cross-user leak, confirmed), but it is not pinned to the path's `debt_id`: `POST /debts/{A}/repayments` with a `client_id` previously spent on debt B's repayment — or on B's PRINCIPAL via `POST /debts` — answers 200 with B's detail, i.e. "your repayment landed" for a different debt. Only a buggy client reuses a key across operations, so this is a semantics gap, not a hole. Minimal fix: in the repayment route, `if existing.debt_id != debt_id: raise _unprocessable("CLIENT_ID_IN_USE")` (the code already exists for the sibling case). Same route-level tightening is not needed on `POST /debts` (no addressed resource there).

3. **MINOR** — `apps/api/src/budget_api/routers/debts.py:511 and 697`. An explicit `"account_amount_minor": null` on either PATCH is refused with `DEBT_ACCOUNT_AMOUNT_REQUIRED`, the code that everywhere else means "cross-currency and absent". On an equal-currency debt there is no account-amount field on the form, so a client mapping that code to a field error will point at nothing. The field is genuinely optional on the wire and `update_movement` already treats `None` as "copy/keep"; minimal fix: drop the `account_amount_minor` entry from both null-check tuples so null ≡ omit (the PATCH "null = recompute" rule: equal → copy, cross → keep).

4. **MINOR** (tests) — `apps/api/tests/test_debts_money.py:423-444`. The repayment-edit ceiling's PASS arm is exercised (4 000→7 000 under principal 10 000: a naive `repaid + new` would refuse it, so the `− stored` term is real), but the REFUSE arm of `update_movement` for a repayment (`DEBT_REPAYMENT_EXCEEDS_REMAINING` from the edit path, l.313-314) is never hit — someone can delete that `if` and the suite stays green. One extra request in the same test (PATCH `amount_minor: 10_001` → 422) pins it; no new test.

5. **MINOR** (tests) — `CLIENT_ID_IN_USE` is an accepted deviation with its own code and zero coverage; `check_due_on` was made public "because the PATCH route judges the EFFECTIVE pair", but only the create arm is tested (`test_debts.py:152`). Two one-line additions to the existing tests (`POST /transactions` with key K then `POST /debts` with K → 422 `CLIENT_ID_IN_USE`; PATCH `opened_on` past `due_on` → 422 `DEBT_DUE_BEFORE_OPENING`). Neither is a reason to block.

6. **NIT** — `apps/api/src/budget_api/routers/statement_imports.py:949-970` (`_reject_unreplaceable`): two round trips (transfer scalar, then debt scalar) where one `select(kind, debt_id)` over `wanted` answers both; the apply-side twin (`_replaceable_targets`) already does it in one query.

7. **NIT** — `apps/api/tests/test_debts_money.py:500-506`: the class docstring says "the two CHECKs", but the first test pins the partial UNIQUE INDEX (`uq_transactions_debt_principal`), not a CHECK. Wording only.

## Conformance notes (no action)

- Money rule in `update_movement` enumerated over (moved?, new == row?, new == debt?, sent?): every combination either copies (new == debt), keeps the stored integer only when the currency is unchanged (new == row ≠ debt), or demands `account_amount_minor` (new ∉ {row, debt}). No path restamps `currency` while keeping `amount_minor`, no cross-currency value is copied as equal; account currency is create-only so `row.currency` == stored account's currency always holds. Principal-shrink ceiling (`new < repaid`) and the create/repayment ceilings are correct; lock precedes totals in both call sites (modulo finding 1).
- Scoping: every query in `debt_reads`, `debt_access`, `debt_writes`, `tx_idempotency` carries `user_id`; `load_own_repayment` pins `debt_role='repayment'`; 404 `DEBT_NOT_FOUND` is the first guard on every `{debt_id}` route (the stranger cases in `TestAccess` prove 404 before the null-check 422s).
- `_NOT_TRANSFER_OR_DEBT` in all four `tx_totals` passes; `DELETABLE_BY_REPLACE` in preview counters, the delete, and `_replaceable_targets`; `_reject_debt_movement` right after the 404 on PATCH and DELETE; CSV `debt_id` appended last with both existing export tests updated.
- Idempotency: `client_id` sits only on the inserted movement; both routes select-first then recover from `IntegrityError` via rollback → re-select; replay on `POST /debts` resolves row → `debt_id` → `_detail` (the plan's named risk, handled).
- MCP: `params=` curated for `amount_minor`/`account_amount_minor` on all three writes; `# MCP: no` with a reason on the two DELETEs and the repayment PATCH; snapshot diff is 263 pure additions, `source.*` untouched; count pins 22/40, PAT pairs and never-list updated.
- Tests: no vacuous or duplicate tests found; the borrow test is the income-kind contrast of the lend test, not a copy.

## Verdict

Conformant to the agreed architecture and the three accepted deviations; the single-exclusion-point, no-oracle, migration and MCP items all check out, and `alembic check` is clean. The one thing to fix before merge is finding 1: the repayment-edit ceiling reads the stored amount from a pre-lock object, so the `SELECT … FOR UPDATE` does not actually serialize two edits of the same repayment and a shrink-then-raise race can drive `remaining` negative — a two-line reorder (lock first, `refresh(row)`) closes it. Findings 2-5 are small tightenings and cheap test contrasts that can land in the same pass; 6-7 are optional.
