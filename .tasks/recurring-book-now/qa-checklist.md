# Секция A — PYTEST-реестр (owner: backend-engineer)

### P-1 — двойной book одного срока: списано ровно один раз
Шаблон с pending-сроком `D`. (a) POST book `{due_on: D}` → 201; повтор того же
тела → 422 `DUE_DATE_NOT_PENDING`; в БД **ровно одна** транзакция с этим
`recurring_template_id`, ватермарка == `D` (не сдвинулась дважды).
(b) Конкурентная ветка: два запроса в двух сессиях одновременно → ровно один
201 и ровно один 422, одна строка (проверка, что валидация живёт ВНУТРИ
`with_for_update`, а не до замка). Мутация «читать шаблон без FOR UPDATE»
обязана валить (b).

### P-2 — ручной book и материализатор не книжат один срок дважды
Book сегодняшнего срока через сервис/эндпоинт → затем `materialize_due(today)`
(тот же путь, что ночная джоба и boot catch-up) → транзакций по-прежнему одна,
ватермарка не двинулась. Обратный порядок (сначала джоба, потом book того же
`due_on`) → 422 `DUE_DATE_NOT_PENDING`, второй строки нет.
Живьём материализатор по HTTP недостижим — это доказательство здесь и только
здесь (частично дублируется условным LV-4).

### P-3 — досрочный book будущего срока
`due_on` = первый pending-срок в будущем (например today+10) → 201;
`occurred_at == today` (D3), **не** `due_on`; ватермарка == `due_on` (в будущем);
последующий `materialize_due(today)` НЕ создаёт строку (фильтр `< today`);
`next_due_on` шаблона — строго следующий срок после `due_on`, а не тот же самый.
Мутация «ватермарка = today» обязана валить последний пункт (иначе срок
перекнижится ночью — прямое задвоение).

### P-4 — сырая ватермарка при задолженности (не перепрыгиваем арреарс)
Ватермарка отстала (pending-срок в прошлом). (a) book даты, которую рисует
виджет (floor по today, т.е. НЕ первый pending) → 422 `DUE_DATE_NOT_PENDING`,
ватермарка не тронута; (b) book первого pending (прошлого) срока → 201,
ватермарка сдвинулась ровно на этот срок, остальные арреарс-даты остались
pending. Инвариант «ватермарка двигается только через списанные даты» (D2).

### P-5 — отказы и no-oracle (одним тестом-таблицей)
- paused → 422 `RECURRING_TEMPLATE_PAUSED`;
- (amended per PM 2026-08-23, task.md D5) счёт шаблона архивирован ПОСЛЕ
  создания → book УСПЕШЕН, 201, строка на архивном счёте — зеркало джобы
  (recurring_jobs.py:131-141, решение B2/MINOR-1); кода `ACCOUNT_ARCHIVED` на
  эндпоинте НЕ существует;
- чужой и несуществующий `template_id` → байт-в-байт одинаковый 404
  `RECURRING_TEMPLATE_NOT_FOUND`; **порядок гейтов**: чужой паузнутый шаблон →
  всё равно 404, не 422 (иначе оракул существования, conventions.md);
- `due_on` вне грамматики, за `end_date`, до `start_date`, в далёком прошлом →
  тот же 422 `DUE_DATE_NOT_PENDING` (один код на все, D2);
- тело: `amount_minor` = 0 / отрицательный / не-int, отсутствующий или
  невалидный `due_on` → 422 (Pydantic);
- во всех отказных ветках транзакций не создано и ватермарка не тронута.

### P-6 — override суммы и эквивалентность конструктора (D7)
`amount_minor` в теле меняет ТОЛЬКО транзакцию: строка несёт override, а
шаблон после запроса имеет прежний `amount_minor` (перечитать из БД).
Без `amount_minor` — сумма шаблона. Плюс эквивалентность: строка, созданная
эндпоинтом, и строка, созданная `materialize_due` для того же шаблона,
совпадают по всем скопированным полям (account_id, currency-штамп, category,
merchant, note, kind, `recurring_template_id`) и обе несут base-снапшот
(`base_amount_minor`/`base_currency`) на дату `occurred_at`. Одна фабрика, а не
второй механизм.

### P-7 — контракт, PAT, замок на write-путях (указатель, новых тестов минимум)
- пара `openapi.json` ↔ `schema.d.ts` — существующий drift-тест
  `tests/test_openapi_export.py`; в экспорте есть `POST /recurring/{template_id}/book`
  с 201 TransactionRead и 422-arm с новыми кодами;
- PAT fail-closed: пары в `PAT_ALLOWLIST` НЕТ (D8) → вызов book PAT'ом
  (даже scope=full) → 403 `TOKEN_ENDPOINT_FORBIDDEN`. Один тест, дешевле любого
  живого прогона;
- D6: после перевода write-путей `_load_own` на `with_for_update` существующий
  recurring-сьют (pause/unpause, PATCH start_date, B3-перенос счёта) остаётся
  зелёным — регрессия, не новые тесты.

## Предусловия
- API :8010, **`RECURRING_SCHEDULER_ENABLED=false`** (кроме LV-4): включённый
  boot catch-up материализует сегодняшние сроки при рестарте и обесценит счётчики.
- Пользователь `qa-book-a@budgetqa.dev` / `Qa!Test1234` — **логин один раз**,
  токен переиспользуется во всех TC (чужой шаблон живьём не гоняем, второй
  пользователь не нужен — P-5).
- Все даты — от **UTC**-сегодня; не запускать в окне ±15 минут от 00:00 UTC.
- Фикстуры — curl'ом: счёт RUB `A1`, категория expense; шаблоны
  `T-DUE` (monthly, day_of_month = сегодняшнее число ≤28, без start_date →
  сегодняшний срок pending), `T-DUP` (такой же, отдельный — чтобы LV-2 не
  зависел от LV-1), `T-FUTURE` (monthly, start_date = today+10).
- Порядок обязателен: фикстуры → LV-1 → LV-2 → LV-3. LV-2 и LV-3 работают на
  собственных шаблонах и от LV-1 данными не зависят.
- Ватермарка по HTTP не отдаётся: где нужна — читаем `SELECT last_materialized_on`
  из Postgres :5443 (read-only), это evidence, а не отдельный TC.

### LV-1 — сквозной happy path: сервер поднялся, деньги сошлись во всех числах
- **Method/Endpoint**: `POST /recurring/{T-DUE}/book`, body `{"due_on":"<today>"}`
- **Зачем живьём**: единственная проверка, что маршрут вообще существует на
  поднятом сервере, и что числа, которые видит пользователь, складываются
  одинаково в четырёх независимых источниках. Ни один из них pytest не собирает
  вместе.
- **Ожидание**: 201 TransactionRead; `recurring_template_id` == T-DUE,
  `occurred_at` == today, `amount_minor` == сумма шаблона, `currency` == RUB,
  base-снапшот заполнен. Затем без повторного логина:
  `GET /recurring` → `next_due_on` шаблона уехал на следующий период,
  `amount_minor` шаблона прежний; `GET /recurring/upcoming?days=30` → списанного
  срока в списке НЕТ; `GET /accounts` → `balance_minor` счёта A1 уменьшился ровно
  на сумму (для kind=expense); `GET /transactions?account_id=A1` → ровно одна
  новая строка. Плюс `GET /health` 200 и наличие роута в живом `/openapi.json`.
- **curl**:
```bash
  TOKEN=$(curl -s -X POST http://localhost:8010/auth/login -d 'username=qa-book-a@budgetqa.dev&password=Qa!Test1234' | jq -r .access_token)
  curl -s -X POST http://localhost:8010/recurring/$T_DUE/book \
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
    -d "{\"due_on\":\"$TODAY\"}" | jq '{id,occurred_at,amount_minor,recurring_template_id,base_amount_minor}'
```
- **Статус**: ⏸ pending

### LV-2 — двойной клик по «+»: реальный замок на реальных соединениях
- **Method/Endpoint**: два одновременных `POST /recurring/{T-DUP}/book` с
  идентичным телом `{"due_on":"<today>"}`
- **Зачем живьём** (сознательный дубль P-1b): pytest доказывает логику в одном
  процессе и на тестовой сессии; здесь проверяется реальный row-lock на боевом
  пуле соединений uvicorn+asyncpg — это ровно сценарий «пользователь нажал
  кнопку дважды за 200 мс», и цена ошибки — деньги.
- **Ожидание**: ровно один 201 и ровно один 422 `DUE_DATE_NOT_PENDING` (не два
  201, не 500, не таймаут); `GET /transactions` → одна строка по T-DUP; баланс
  A1 сдвинулся один раз; третий, уже последовательный, POST того же тела → 422.
- **curl**:
```bash
  for i in 1 2; do curl -s -o /tmp/book$i.json -w "%{http_code}\n" -X POST \
    http://localhost:8010/recurring/$T_DUP/book -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" -d "{\"due_on\":\"$TODAY\"}" & done; wait
```
- **Статус**: ⏸ pending

### LV-3 — досрочное списание с правкой суммы: что списалось и что осталось
- **Method/Endpoint**: `POST /recurring/{T-FUTURE}/book`,
  body `{"due_on":"<today+10>","amount_minor":123456}`
- **Зачем живьём**: комбинация «дата среза ≠ дата денег» + override — то, что
  пользователь увидит как расхождение между виджетом, шаблоном и балансом;
  собирается из трёх источников сразу.
- **Ожидание**: 201; `occurred_at` == **today**, не today+10; `amount_minor`
  == 123456 (override). Далее: `GET /recurring` → у T-FUTURE `amount_minor`
  ПРЕЖНИЙ (шаблон не переопределён, D4), `next_due_on` — срок ПОСЛЕ today+10;
  `GET /recurring/upcoming?days=30` → списанного срока нет, следующий есть;
  `GET /accounts` → баланс A1 сдвинулся на 123456, не на сумму шаблона;
  SQL-evidence: `last_materialized_on` == today+10.
- **Статус**: ⏸ pending

### LV-4 (УСЛОВНЫЙ, вне потолка) — boot catch-up не перекнижит списанное вручную
- **Предусловие**: требуется рестарт **нашего** api-контейнера с включённым
  планировщиком. Правок `docker-compose.yml`/`.env` не делаем. Если рестарт не
  санкционирован оркестратором — TC остаётся 🚫 blocked, покрытие целиком
  ложится на **P-2**, и это осознанно.
- **Ожидание**: после LV-1 (сегодняшний срок T-DUE списан вручную) рестарт →
  безусловный boot catch-up (D5 recurring) → `GET /transactions?account_id=A1`
  показывает то же число строк, что до рестарта; баланс A1 не изменился.
- **Статус**: ⏸ pending
