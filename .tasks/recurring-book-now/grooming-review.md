## QA-программа (сжата по PM)
2–3 живых браузерных сценария (R7): предзаполнение из виджета; из списка с
правкой суммы; архивный счёт → внятный отказ формы. pytest не нужен (сервер
не трогается); vitest — только маппер, если нетривиален. Реестр вычеркнутого:
вся идемпотентность/задвоение/stale-сценарии первой версии сняты вместе с
семантикой материализации — проверять нечего, механизма нет.

## Ключевые решения (указатели)
- task.md R1–R7: ярлык, не списание; ватермарка не трогается; двойное нажатие —
  ответственность пользователя (PM); paused-шаблон кнопку ИМЕЕТ (заготовка
  операции, не списание); архивный счёт — обычный отказ формы, без спецмеханизма.
- Дата по умолчанию (R4, решено без вопроса пользователю): виджет → due_on
  строки (клик в конкретный датированный срок), список → today (ярлык = «записать
  сейчас», конкретного срока в фокусе нет).
- Решения PM второй волны (полный текст — plan-web.md, блок «Решения PM
  2026-08-23»): `currentId`-фикс обязателен + тест против молчаливой подмены
  архивного счёта; `merchant ?? name` утверждён с обязательным комментарием в
  маппере (разница данных, не небрежность); правка копии
  `transaction.accountArchived` в shared разрешена, мобилка проверяется
  typecheck'ом.

## Открытый риск (решение за PM/пользователем, скоуп не расширяем)
Ручная запись через ярлык НЕ отменяет автосписание того же срока: 1-го числа
джоба спишет шаблон, даже если пользователь записал этот платёж руками 23-го.
Это система+пользователь, а не «пользователь дважды». В переопределённом скоупе
принято как поведение; фиксирую, чтобы удивление будущего пользователя имело
адрес.

по кнопке когда-нибудь вернётся), follow-ups 1–2 оформлены.
