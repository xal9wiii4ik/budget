# Implementation Plan (backend): stats-advisor (roadmap 4.1 / 4.4 / 4.5; 4.2 web + 4.3 mobile are NOT mine)

Scope-grooming plan. Structured **by subtask**, each sized for one engineer run,
with explicit dependencies. Nothing is implemented in this run. Architecture
decisions are cited as **Dn**; every claim below was verified against the working
tree (files + line numbers cited inline).

**Order:** B1 → B2a → B2b → B3. Strictly sequential: B1 and B2a both touch
`routers/goals.py`; B1/B2b/B3 each end in a contract regen and two regens must
never race on `openapi.json` (the receipts §5 argument, reused at currencies-goals).
B3 is otherwise independent and may be resequenced ahead of B2 if the web wants
the export first — the advisor is the binding user requirement, so it goes first
by default.

## Approach

Four subtasks, bottom-up. **B1** builds the aggregate layer: the new pure
`domain/periods.py` (which also absorbs `_shift_month` from `routers/goals.py:113`
per D5), two new functions on the existing `services/tx_totals.py` (D2 — grow,
never fork), and the thin three-endpoint `routers/stats.py` (D4), plus the D14
`le=` bounds. **B2a** is three behaviour-preserving extractions that the advisor
needs as plumbing — `ai_gate.py` (D11), the `user_rl_key(namespace)` factory (D10),
`services/goal_reads.py` (D8) — with zero contract change and the existing
receipts/goals suites as the guard. **B2b** is the advisor proper: the
`services/advisor.py` seam (D7, the `receipt_parser.py` template), the SSE
`POST /advisor/ask` (D9/D10), settings, and the contract regen that the web's
hand-written `askAdvisor` types against. **B3** is the CSV export (D13).

B2 is split because the architect's single B2 would have carried three refactors
of shipped routers *plus* a new external-integration seam *plus* the first
streaming endpoint in the codebase *plus* a regen — two review surfaces in one
run. Split, B2a is a diff a reviewer can read as "nothing changed" (no contract
regen at all), and B2b is a diff that is entirely new code. The cost is one extra
run; the benefit is that a receipts/goals regression in B2a can never hide inside
the advisor diff.

Cross-cutting rules reused everywhere: one conversion resolution
(`tx_totals`' three-bucket algorithm — every new aggregate rides it), minor units
end-to-end with every minor↔major crossing through `currency_exponent()` (AM-5),
exclude-and-flag on a missing rate (never error, never mix currencies), no-oracle
user scoping on every new query.

**Actual project commands** (there is no `make` in this repo — verified: no
Makefile at the root or in `apps/api`):

- tests: `cd apps/api && uv run pytest` (or `pnpm --filter @budget/api test`)
- lint: `pnpm --filter @budget/api lint` (= `ruff check . && ruff format --check .`)
- types: `pnpm --filter @budget/api typecheck` (= `pyright`, strict)
- contract regen, BOTH artifacts in one command: **`pnpm openapi`** from the repo

  `packages/api-client/src/generated/schema.d.ts`). Commit the two files

- client gates after a regen: `pnpm --filter @budget/api-client typecheck` and

## `domain/periods.py` (pure; stdlib `datetime` + `enum` only, imports nothing internal)

```python
MONTH_PATTERN = r"^\d{4}-(0[1-9]|1[0-2])$"     # moved verbatim from routers/transactions.py:64
QUARTER_PATTERN = r"^\d{4}-Q[1-4]$"

class PeriodUnit(StrEnum):
    month = "month"; quarter = "quarter"; year = "year"; custom = "custom"

def shift_month(first_of_month: date, months: int) -> date        # MOVED from routers/goals.py:113, body verbatim
def month_key(d: date) -> str                                     # "YYYY-MM"
def month_bounds(month: str) -> tuple[date, date]                 # ("2026-08") -> (2026-08-01, 2026-09-01) [from, to_exclusive)
def quarter_bounds(quarter: str) -> tuple[date, date]             # ("2026-Q1") -> (2026-01-01, 2026-04-01)
def year_bounds(year: int) -> tuple[date, date]
def previous_period(unit: PeriodUnit, date_from: date, date_to_exclusive: date) -> tuple[date, date]
    # month -> (shift_month(from,-1), from); quarter -> (shift_month(from,-3), from);
    # year -> (date(y-1,1,1), from); custom -> (from - (to_exclusive - from), from)
    # INVARIANT for all four: prev_to_exclusive == date_from.
```

All bounds are `[from, to_exclusive)` internally; the wire echoes **inclusive**
`to` (`to_exclusive - 1 day`). Inputs are pattern-validated at the Query layer
(AM-6) so these functions never parse-then-catch.

## `services/tx_totals.py` growth (D2)

```python
@dataclass(frozen=True)
class MonthTotals:
    month: date            # first-of-month
    income_minor: int
    expense_minor: int
    unconverted_count: int

async def monthly_converted_totals(
    session: AsyncSession, user_id: uuid.UUID, base: str, *,
    months: int, ending_first: date,
) -> list[MonthTotals]:
    """Dense ASCENDING series of `months` calendar months ending at `ending_first`."""

@dataclass(frozen=True)
class MerchantTotal:
    merchant: str
    total_minor: int
    tx_count: int

@dataclass(frozen=True)
class MerchantTotals:
    items: list[MerchantTotal]
    unconverted_count: int

async def merchant_converted_totals(
    session: AsyncSession, user_id: uuid.UUID, base: str,
    date_from: date, date_to_exclusive: date, *,
    kind: TransactionKind, limit: int,
) -> MerchantTotals:
```

Shape (decided, not latitude — D2):

- `monthly_converted_totals`: window = `[shift_month(ending_first, -(months-1)),
  shift_month(ending_first, 1))`. **One** grouped pass over the whole window —
  `GROUP BY date_trunc('month', occurred_at), kind` with the *same* CASE
  expression as `converted_totals` (tx_totals.py:71-74; the arm order is
  load-bearing) — plus **one** bucket-3 scan over the whole window, folded per
  month in Python (`row.occurred_at.replace(day=1)` is the bucket key). NOT N
  calls to `converted_totals`. Empty months are emitted as zeros; the caller's
  `ending_first` is included. `date_trunc` returns a timestamp — read
  `bucket.year/.month`, the shipped `goal_progress` pattern (goals.py:620).
- `merchant_converted_totals`: `WHERE merchant IS NOT NULL AND kind = :kind`,
  same CASE, `GROUP BY merchant`; bucket-3 fold-in over the same predicate; the
  top-`limit` cut applied **after** the fold-in. Order `total_minor DESC,
  merchant ASC` (the secondary key is for determinism — an unordered tie makes
  tests flaky and pagination-free UIs jitter).
- **Pinned decision (gap in D2):** a row with no rate is excluded from BOTH
  `total_minor` and `tx_count` and counted once in `unconverted_count`; a merchant
  left with zero *included* rows is omitted from `items` entirely. Rationale: the
  count and the total must describe the same row set, and a `(merchant, 0, 0)`
  row would read as "spent nothing here", which is a lie — the honest signal is
  `unconverted_count`. Pinned by test B1-13.
- `converted_totals` is NOT refactored; the goals free-balance 3-call loop
  (goals.py:191) is NOT moved onto the new function (meta-review-pinned deviation 5).

## Why receipts calls the guard inline instead of `Depends(...)`

The obligation is "EXACT byte shape of the receipts 503 unchanged". Making it a
route-level dependency would change *ordering*, not just bytes: FastAPI solves
router/route-level dependencies before the endpoint's own parameters, so an
**unauthenticated** parse request on an unkeyed server would answer 503 instead of
today's 401, and the slowapi wrapper (which today counts the 503 against quota)
would stop seeing it. An inline call at the same statement position is


**Load-bearing implementation constraints (not latitude):**

1. **All DB work happens BEFORE the `StreamingResponse` is returned.** FastAPI
   (≥0.106) exits `yield` dependencies *before* the response body is streamed, so
   the `get_session` session is closed by the time the generator runs. The handler
   assembles the full `AdvisorContext` (aggregates + goals + category names +
   profile), then returns `StreamingResponse(_events(...))` whose generator touches
   **no** session, no ORM object, only the frozen dataclass and the seam. A
   violation is a greenlet/closed-session crash mid-stream, not a test failure.
2. Context assembly reuses the SAME functions the stats endpoints and the goals
   screen use (D7/D8): `monthly_converted_totals`, `converted_totals`,
   `merchant_converted_totals` (kind=expense, limit=10),
   `goal_reads.assemble_goal_reads`, and `category_access.visible_categories_clause`
   for id→name (include-archived: an archived category still owns its history).
   No `advisor_context.py` module (D7 YAGNI).
3. **Window (gap-fill in D7, see OQ-2): the 3 FULL calendar months ending with the
   last complete month** — `[shift_month(current_first, -3), current_first)`,
   current partial month EXCLUDED. Rationale: the goals portfolio in the same
   prompt is derived from exactly that window (`_FREE_BALANCE_MONTHS`, goals.py:70),
   and comparing a 9-day partial month against three full ones is how an advisor
   invents a fake trend.
4. The event generator emits **exactly one terminal event** and never raises:
   ```
   event: delta\ndata: {"text": "..."}\n\n     (0..n)
   event: done\ndata: {}\n\n                   (terminal, success)
   event: error\ndata: {"detail": "ANTHROPIC_ERROR"}\n\n   (terminal, failure)
   ```
   `data` is always ONE-LINE JSON (`json.dumps`) — SSE frames cannot carry raw
   newlines and a model answer is full of them. `AdvisorError` (from any position,
   including before the first delta) → the `error` event; `asyncio.CancelledError`
   is NOT swallowed (a client disconnect must close the generator).
   **Decision D9 delegated to the router:** a pre-first-delta failure is *also* an
   `error` event, not a JSON status. The alternative (pull the first chunk eagerly
   so an immediate SDK failure can be a 502) buys one status code at the price of
   holding the response open before the 200, and the client already has to handle
   the `error` arm. Pinned by test B2b-2.
5. Headers: `media_type="text/event-stream"`, `Cache-Control: no-store`.
6. No 422 `responses` override: the caps below are Pydantic validators, so the
   auto `HTTPValidationError` is the only honest 422 arm (Disagreement 3).

# Disagreements with the architecture (numbered — none silent)

1. **D9's guard-order sentence** ("the slowapi wrapper runs before the endpoint
   body, so a 503 response still consumes quota — same behavior as receipts
   parse"). Once the guard is extracted per D11 and used as a *dependency*
   (which is the only form that makes it shareable), it resolves BEFORE the
   slowapi wrapper, so an `AI_NOT_CONFIGURED` 503 does **not** consume advisor
   quota. I am shipping that order deliberately: an unkeyed 503 costs no DB and no
   Anthropic spend, so limiting it protects nothing, and the binding UI
   requirement is that an unkeyed server keeps answering "ключ не настроен" —
   which a consumed quota would turn into "RATE_LIMITED" on the second click.
   Receipts keeps its inline call site, so its shipped behaviour (incl. quota
   consumption and 401-before-503) is byte-identical. Pinned by test B2b-4.
   Cost to veto: move the `Depends` into the body as an inline `await` — one line,
   one test flip.
2. **D7's "imports config + schemas only"** for `services/advisor.py` → **config +
   stdlib only**. Stricter, same spirit: with module-local frozen dataclasses,
   "there is structurally nowhere to put a `Transaction` row" is a property of the
   import graph rather than of the reviewer's attention. Cost: a ~20-line mapping
   in the router, which the router owes anyway (it maps ids to category names).
3. **D9's 422 arm** ("honest anyOf union … `AdvisorError`"). The two history caps
   (≤10 turns, ≤8000 chars) are expressible as Pydantic validators, so they
   surface as `HTTPValidationError` and the advisor has **no** business 422 code
   at all. Declaring an anyOf union whose `AdvisorError` arm no route can emit
   would be the exact "the generated type lies about one arm" failure the AM-5
   pattern exists to prevent — inverted. `AdvisorError` is still declared, as the
   model for the 503 and 429 arms. (Stats KEEPS the union: `PERIOD_ANCHOR_REQUIRED`
   is a real cross-field business rule that no query-param validator can express.)

# Risks

- **Streaming + closed sessions.** The single biggest landmine in this scope:
  FastAPI ≥0.106 exits `yield` dependencies before the response body streams, so
  any DB access inside the advisor or CSV generator is a runtime crash *after* a
  200 has been sent (i.e. a half-written stream, not a clean 500). Mitigated by
  design (context pre-assembled; CSV generator owns its session from the
  sessionmaker) and by tests that consume the full stream rather than just the
  status line.
- **slowapi × `StreamingResponse`.** `headers_enabled=False` (rate_limit.py:45)
  means slowapi's success-path header injection never runs, so the wrapper should
  not touch the generator — but this is the first streaming route under a limiter.
  Verify at implementation that the response is returned un-consumed (test B2b-5
  covers the 429 arm; test B2b-1 covers the streaming-through-the-wrapper arm).
- **OpenAPI 200 media type** for the two non-JSON routes: FastAPI may keep an
  `application/json` arm alongside the declared one. STOP-and-report rather than
  hand-editing artifacts (O-8).
- **D14 is a contract narrowing**, not an addition: a client sending an absurd
  amount that used to be accepted now gets a 422. O-2's max() check is what turns
  "should be fine" into evidence. `ContributionCreate` needs the bound on BOTH
  signs — a `le=` alone would leave `-1e18` legal.
- **Reverse-proxy buffering** (1.7 deploy, not this scope): an nginx in front of
  the SSE endpoint will buffer the stream into uselessness without
  `proxy_buffering off` / `X-Accel-Buffering: no`. Flagged here so deploy grooming
  inherits it; deliberately NOT coded now (no proxy exists yet).
- **Prompt cost/quality drift.** `advisor_model` is a dated Sonnet snapshot
  (verified present in the installed SDK's model listing); a future SDK bump that
  drops the snapshot is a startup-time failure only on the first real call, not at
  import. Env-swappable by design.
- **Merchant grouping is verbatim** (OQ-4): visible duplicate rows on the real
  screen are the recorded re-visit trigger, not a bug report.
