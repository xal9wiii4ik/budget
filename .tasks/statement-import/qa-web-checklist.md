# QA Web Checklist: statement-import (браузерные user-journeys, apps/web)

## Scope и данные
Покрывает S4 (upload → предпросмотр → сверка/замена) глазами пользователя в браузере.
API-уровень (парсер, матчинг, идемпотентность, no-oracle, лимиты) — у qa-engineer, здесь не дублируется.
Данные: ТОЛЬКО `qa-*@budgetqa.dev`. Реальную выписку не использовать — синтетические cp1251-фикстуры
в формате Приорбанка: `fixture-main.csv` (2 секции, шапка BYN, строка с парой PLN, строка CH Debit,
два байт-одинаковых платежа, нулевой оборот, хвост «Заблокированные суммы»), `fixture-garbage.csv`
(не-CSV мусор), `fixture-usd.csv` (валюта шапки ≠ валюте счёта), `fixture-big.csv` (генерённая, ~600 строк).
QA-cadence: полный прогон ОДИН раз, в конце скоупа (после S4). Все WJ — кандидаты на живой прогон.

### WJ-1: Полный happy-path сверки [live]
- **Цель**: путь «сверить» от файла до транзакций в списке без перезагрузки страницы.
- **Шаги**: залогиниться → выбрать счёт BYN → загрузить `fixture-main.csv` → в предпросмотре: строка
  `new` имеет дефолт import, `exact`/`similar` — skip; similar подсвечена; у P2P-строки виден флаг
  «возможно перевод»; на одной строке сменить решение (skip→import) и категорию → apply.
- **Ожидаемое**: отчёт apply (created/skipped/already_existed); транзакции появились в /transactions,
  merchant = «Операция», у PLN-строки видна пара «потрачено/списано»; баланс счёта и /stats
  обновились БЕЗ reload; заблокированные/нулевые показаны счётчиком «пропущено N», не строками.
- **Network/console**: POST multipart → 201; PATCH строки → 200 (тело — дифф); apply вызван ровно
  один раз; после apply — инвалидации transactions/stats/accounts (рефетчи видны); console чист.

### WJ-2: Replace-путь — предупреждение ДО, честный список ПОСЛЕ [live]
- **Цель**: необратимое «заменить с даты X» невозможно совершить случайно и не врёт о последствиях.
- **Шаги**: счёт с существующими транзакциями в периоде, среди них: одна с чеком, одна из плана цели,
  один перевод → загрузить фикстуру → путь «заменить», дата X внутри периода → рассмотреть preview →
  подтвердить → проверить список. Отдельно: дата X < period_from.
- **Ожидаемое**: preview ДО подтверждения показывает: сколько удалится всего, сколько с чеком/целью/
  шаблоном, «переводы останутся: N», сколько создастся; подтверждение — явный ConfirmDialog (Esc/бэкдроп
  не подтверждают, кнопка не под курсором по умолчанию); после replace: перевод жив, старые строки
  диапазона удалены, новые созданы; X < period_from → человеческая ошибка, replace недоступен.
- **Network/console**: GET replace-preview ДО POST replace; POST replace один раз; 422
  REPLACE_FROM_OUT_OF_RANGE показан копией из ERROR_MESSAGES, не кодом; console чист.

### WJ-3: Повторная загрузка того же файла — дублей нет [live]
- **Цель**: пользователь загружает тот же файл второй раз и не может испортить данные.
- **Шаги**: после WJ-1 загрузить `fixture-main.csv` в тот же счёт ещё раз → предпросмотр → apply.
- **Ожидаемое**: строки применённых операций — `exact` с дефолтом skip (включая ОБА байт-одинаковых
  платежа — каждый сматчен со своей транзакцией, не оба с одной); apply не создаёт дублей, в отчёте
  виден already_existed/skipped; список /transactions и суммы /stats не изменились.
- **Network/console**: повторный POST → 201 (новая сессия, старая parsed вытеснена); никаких
  дублирующих POST /transactions; console чист.

### WJ-4: Ошибки по-человечески [live]
- **Цель**: плохой файл не оставляет пользователя с кодом ошибки или сломанным экраном.
- **Шаги**: (а) загрузить `fixture-garbage.csv`; (б) `fixture-usd.csv` в BYN-счёт; (в) файл > 1 МБ.
- **Ожидаемое**: каждый случай — понятное сообщение на языке UI (что не так и что делать: «не похоже
  на выписку Приорбанка», «выписка в USD, счёт в BYN»); форма остаётся рабочей, повторная загрузка
  корректного файла проходит; никакой «сессии-призрака» в UI (422 = сессия не создана).
- **Network/console**: 422 STATEMENT_PARSE_FAILED / STATEMENT_CURRENCY_MISMATCH / STATEMENT_TOO_LARGE;
  после 422 нет GET сессии/rows; в console нет unhandled rejection.

### WJ-5: Большой предпросмотр (~600 строк) [live]
- **Цель**: предпросмотр годовой выписки листается без подвисаний.
- **Шаги**: загрузить `fixture-big.csv` → пролистать предпросмотр до конца → отфильтровать по
  match_status (если фильтр есть в UI) → сменить решение на строке в глубине списка.
- **Ожидаемое**: интерфейс отзывчив (ощутимых фризов при прокрутке/пагинации нет), позиция и принятые
  решения не теряются при подгрузке страниц; PATCH одной строки не перерисовывает/перезапрашивает весь список.
- **Network/console**: GET rows постранично с limit ≤ 200, offset — pageParam (не растущий вал
  запросов); один PATCH → без полного рефетча всех страниц; console без warning'ов о produce/keys.

## Summary — живой прогон 2026-08-27 (qa-web-engineer)

Окружение: свой API :8020 + свой vite :5183, одноразовая БД `budget_qa_s4` в Postgres 5443,
пользователь `qa-s4-web@budgetqa.dev`. Файл через браузер загружался реальным `<input type=file>`
внутри приложения (same-origin iframe-харнесс: инструмент QA не умеет заполнять file input,
сам upload идёт кодом приложения — сгенерированный клиент, FormData, cp1251 в теле).

- **Загрузка через браузер (первый multipart проекта)** — ✅ OPTIONS preflight 200 → POST 201,
  cp1251 доехал, навигация на `/imports/:id`.
- **WJ-1** ✅ — дефолты new→import, exact/similar→skip; similar подсвечена; флаг «возможно, перевод»
  на CH Debit и CH Payment P2P; PATCH строки → 200 с ТЕЛОМ строки и рефетчем ТОЛЬКО сессии;
  групповое решение по чипу — один POST bulk-decision (не цикл PATCH); apply один раз;
  отчёт created/skipped/replaced/already_existed; в /transactions пара PLN «-1 800,00 PLN / -1 439,63 BYN»,
  баланс счёта пересчитан сервером (1 905,67 BYN — сходится), GET /accounts рефетчится сразу после apply.
- **WJ-2 (replace)** ✅ — превью серверных счётчиков (удалится 6 / с чеком 0 / из плана цели 1 /
  от шаблона 0 / переводы останутся 1 / создастся 5); (а) смена даты сбрасывает введённое число и
  лочит кнопку; (б) неверное число кнопку не открывает (POST не уходит); (в) рассинхрон (транзакция
  создана курлом между превью и подтверждением) → 422 REPLACE_CONFIRMATION_MISMATCH, на экране
  человеческое предложение с ОБОИМИ числами (7 и 6) и обновлённое превью; (г) дата < period_from
  отбита на клиенте копией «Выберите дату между 1 июн. и 30 июн.» (серверный REPLACE_FROM_OUT_OF_RANGE
  проверен курлом). После replace: перевод жив, tx из плана цели и «гоночная» удалены, до даты X всё цело.
  НЕ проверено вживую: `deleted_with_receipt` (нужен чек → MinIO+AI) и `deleted_with_recurring_template`
  (нужна материализация шаблона) — обе строки показаны нулями; закрыты pytest'ом бэкенда.
- **WJ-3** ✅ — повторная загрузка: все применённые строки exact/skip, оба байт-одинаковых платежа
  сматчены с РАЗНЫМИ транзакциями; строка, принудительно поставленная в import, дала
  «Создано 2 / 1 строка была импортирована раньше» — дублей в /transactions нет.
- **WJ-4** ✅ — garbage → «Это не похоже на CSV-выписку Приорбанка…»; USD-шапка в BYN-счёт →
  «Выписка в USD, а счёт в BYN…»; >1 МБ → «Файл слишком большой (предел — 1 МБ)…». После каждого 422
  модалка жива (input и кнопка активны), следующий корректный файл грузится без перезагрузки;
  сессий-призраков в БД нет (только успешные).
- **WJ-5** ✅ — 600 строк: страницы по 200 (offset 0/200/400, limit>200 сервер отбивает 422),
  «Показать ещё» +200 строк за ~200 мс, PATCH строки в глубине — 42 мс и БЕЗ рефетча трёх страниц
  (только GET сессии), 40 шагов прокрутки с форс-лейаутом — 1 мс, решения после подгрузки не теряются.
- Консоль: JS-ошибок и unhandled rejection нет ни в одном сценарии (в логе только браузерные записи
  о статусах 401/422 — 401 это плановое протухание access-токена, координатор молча обновил пару и
  повторил запрос).
