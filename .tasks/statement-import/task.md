# Скоуп `statement-import` — импорт выписки Приорбанка

Запрос пользователя 2026-08-26 с реальным файлом выписки.

## Факты о формате (разобраны по настоящему файлу, не по догадкам)

Образец: `Vpsk_71466782.csv`, период 26.05.2026–26.08.2026, 218 строк операций.

- **Кодировка cp1251**, разделитель `;`, десятичная запятая, разделитель тысяч —
  пробел (`1 800,00`). Файл НЕ в UTF-8: наивное чтение даёт мусор.
- **Шапка**: период, дата выписки, номер контракта с валютой (`......5817 Валюта
  контракта BYN`), номер карты (`........7351 VISA SIGNATURE`), ФИО, остатки.
- **Два уровня**: секция «Операции по ......5817» (контракт) и «Операции по
  ........7351» (карта), у каждой свой заголовок столбцов, свои строки и строка
  итогов «Всего по контракту».
- **Колонки**: Дата транзакции; Операция; Сумма; Валюта; Дата операции по счету;
  Комиссия/Money-back; Обороты по счету; Цифровая карта; Категория операции.
- **Знак**: минус — расход, плюс — доход.
- **Время** бывает `00:00:00` — это «время неизвестно», а не полночь.
- **Категория банка**: 22 различных значения в образце (Магазины продуктовые 59,
  Ресторация / бары / кафе 36, Транспорт - Такси 24, Денежные переводы 16…).
- **Хвост файла**: секция «Заблокированные суммы» — операции, ЕЩЁ НЕ проведённые
  по счёту, с другим набором колонок.

### Подарок формата: валютная пара ложится на нашу модель один в один

В строке в чужой валюте `Сумма`+`Валюта` — это сколько ПОТРАЧЕНО (`-1 800,00 PLN`),
а `Обороты по счету` — сколько СПИСАНО со счёта в его валюте (`-1 439,63 BYN`).
Это ровно наша пара «потрачено / списано», построенная в скоупе
`transaction-details-and-i18n`. Импорт заполняет обе величины БЕЗ конвертации на
нашей стороне: курс банка приходит фактом.

## Чего хочет пользователь

После загрузки файла — ДВА пути:

**1. Сверить.** Показать построчно: что уже есть в приложении, чего точно нет, и
что похоже (suitable). Дальше ручной выбор по каждой строке: заменить, оставить
своё, пропустить.

**2. Полностью импортировать с даты X.** Данные за период с этой даты будут
ЗАМЕНЕНЫ: существующие удалены, новые созданы. Пользователь должен быть
предупреждён об этом явно, до выполнения.

Выписка — по счёту, и импорт тоже по счёту: пользователь выбирает, в какой из
своих счетов заливать.

## Что проработать

1. **Ключ сопоставления.** Что считать «тем же самым»: дата + сумма + описание?
   С каким допуском по дате (банк проводит операцию на 1-3 дня позже
   транзакции — в файле обе даты есть)? Предложи правило для «точно есть»,
   «похоже» и «точно нет», и обоснуй пороги.
2. **Идемпотентность.** У нас ЕСТЬ `client_id` на транзакции (скоуп
   `mobile-offline`, втянут в `mcp-server`). Детерминированный идентификатор из
   строки выписки (счёт + дата + сумма + описание) делает повторную загрузку того
   же файла безопасной по построению. Проверь и используй, а не изобретай второй
   механизм.
3. **Опасность режима «заменить».** Удаление существующих операций за период —
   единственное необратимое действие скоупа. Продумай:
   - что происходит с операциями, у которых есть привязка к чеку, к пункту плана
     цели или к шаблону регулярной операции — эти связи умрут вместе со строкой;
   - показывать ли пользователю ДО подтверждения, сколько именно строк будет
     удалено и сколько из них имеют такие связи;
   - ограничение по счёту: удаляются только операции ВЫБРАННОГО счёта, никогда
     чужие.
4. **Заблокированные суммы — НЕ импортировать.** Они ещё не проведены и придут
   позже обычными строками; импорт создал бы дубль. Пропускать явно, с указанием
   в отчёте, сколько строк пропущено и почему.
5. **Категории банка → наши.** 22 значения в одном файле. Предложи: подставлять
   как подсказку (пользователь подтверждает) или запоминать соответствие, как мы
   уже делаем для мерчантов (`merchant_category_map`). Второе выглядит уместнее.
6. **Переводы между своими счетами.** Строки `CH Debit`/`CH Payment P2P` — это
   может быть перевод между картами самого пользователя. Из выписки одного счёта
   этого не видно. Предложи, как не превратить перевод в доход/расход и не
   испортить статистику — или честно оставь это ручному решению.
7. **Секция контракта против секции карты.** В файле две секции с операциями.
   Реши: импортировать обе в один счёт, дать выбрать, или считать их разными
   счетами.
8. **Размер.** 218 строк за три месяца — за год будет под тысячу. Загрузка,
   разбор и предпросмотр должны это выдерживать без подвисания интерфейса.

## Границы

- Мобильный клиент вне скоупа.
- Формат — Приорбанк. Не строй универсальный парсер под все банки: сделай так,
  чтобы второй формат добавлялся без переписывания, но второй формат сейчас НЕ
  делаем.
- По правилу от 2026-08-25: каждый новый эндпоинт обязан явно ответить, идёт ли
  он в MCP. Загрузка выписки через AI — отдельный вопрос, ответить и обосновать.
