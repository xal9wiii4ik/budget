## Вердикты

- **MAJOR-1 (replace_own на exact-by-client_id молча не исполняется)** —
  СОГЛАСЕН. Случай был помечен мной на диф-гейте как пограничный (7b), ревьюер
  доказал живой пробой, что это дефект: маршрут принимает решение 200-м и
  теряет его, а `already_existed` в отчёте читается как «делать ничего не
  нужно». Выбран вариант (а) — исполнять: гейт в PATCH запретил бы единственный
  осмысленный сценарий replace_own на exact-строке. Исправлено: чтение
  replace-целей до fingerprint-пасса, `freed`-исключение из `existing`,
  delete+insert одной БД-транзакцией; повторный apply сходится (FK SET NULL
  выводит строку из `replacing`). Закреплено тестом
  `test_replace_own_takes_back_a_row_an_earlier_import_created` — красный без
  правки (проверен откатом). Межсессионный корнер «client_id существует через
  ДРУГУЮ транзакцию» осознанно остаётся already_existed без удаления —
  достижим только интерливом двух перекрывающихся сессий, направление
  безопасное, отчёт когерентен.
- **MINOR-2 (отчёт врёт при нескольких строках на одном matched_tx_id)** —
  СОГЛАСЕН: числа — единственная обратная связь необратимой операции.
  Исправлено: `replaced = len(doomed)` (реальные удаления), `created =
  len(pending) − replaced`; инвариант `created + replaced == вставки`
  неотрицателен по построению; докстринги ApplyOutcome/StatementApplyReport
  переписаны честно («суммируются в число строк», не «партиция»). Тест
  `test_two_rows_matching_one_record_delete_it_once` — красный без правки.
- **MINOR-3 (merchant в обход clean_merchant: `""` вместо NULL)** — СОГЛАСЕН.
  Пустое description достижимо с реального парсера (`_cell` → `""`,
  `_parse_operation` не валидирует), поэтому тест написан — отклонение от
  моего брифа в правильную сторону, принимаю. Срез до 255 до вызова (кап
  clean_merchant — ValueError), fingerprint по полному тексту не тронут.
- **NIT-4 (bulk replace_own — 422 без виновника)** — СОГЛАСЕН с вердиктом
  «приемлемо v1». Оговорка ревьюера переносится в план S4: перед bulk
  replace_own веб фильтрует статус по `matched_tx_id`/`candidates[].kind`.
- **NIT-5 (archived-категория не перепроверяется на apply)** — СОГЛАСЕН, что
  поведение верное (отказ всей выписки из-за одной архивации хуже; прецедент —
  recurring materializer пишет в архивную категорию). Задокументировано в
  докстринге apply.py.
- **NIT-6 (двойной _merchant_key)** — СОГЛАСЕН, прибрано (нормализация раз на
  строку).
- **NIT-7 (асимметрия null в StatementRowPatch)** — СОГЛАСЕН, что сервер
  однозначен и грамматика соответствует проектному PATCH-стилю; ловушка для
  клиента — строка в план S4: не слать «пустую форму» целиком.
- **NIT-8 (docs/backend.md не знает про statement-import)** — СОГЛАСЕН; это
  моя обязанность при закрытии скоупа (после S3/S4), зафиксировано.
