# Architecture Plan: rag — semantic search over transactions, cited Q&A, local embeddings

## Context
Filters answer "which rows match"; the owner wants "what did I spend on the car / in Poland / on gifts" (task.md) — a question about MEANING over RU/PL/EN merchant strings, answered with a server total and, in the advisor, with citations the user can click. Structural weight: (1) a 510 MB CPU model living INSIDE the API process on a 2 vCPU / 3.8 GB box, loaded from an artifact that must be pinned, checksummed and never downloaded at request time; (2) a second table that must mirror every write path of `transactions` without touching a single writer; (3) a third seam beside `llm/` (embeddings) with its own fake; (4) a Q&A call whose output is verified against what the server retrieved. Every number below is from `evidence.md`; every decision is `D-*` with a recommendation the engineer may argue.

## Proposed approach
1. `embeddings/` — `Embedder` protocol + `OnnxEmbedder` (onnxruntime + tokenizers + numpy, int8 e5-small) + `FakeEmbedder`; built from settings onto `app.state.embedder`, LOADED in the lifespan, `None` = search not available.
2. `transaction_embeddings` — one row per indexed transaction: `model`, `text_hash`, `vector` BYTEA(1536). PULL indexing: nobody writes it on a write path; staleness = hash mismatch, repaired by a scheduler sweep + boot backfill + a bounded refresh at search time. No pgvector.
3. `GET /transactions/search` (JWT+PAT, `@mcp_tool search_transactions`) → top-k hits with scores + a server total in base currency via `tx_totals`' bucket idiom.
4. `POST /advisor/qa` (JWT-only) → retrieval → ONE `structured()` call (`qa-v1`) → `answer` + verified `citations` (⊆ retrieved, foreign keys dropped and counted).
5. Evals: `retrieval.py` (recall@k, MRR, score distributions; fake in CI, real locally, labelled) and `qa.py` (groundedness via the LLM replay store).

## 1. Embedding seam (`embeddings/`)
- **D-M1 Model = `intfloat/multilingual-e5-small` @ `614241f622f53c4eeff9890bdc4f31cfecc418b3`, files `onnx/model_qint8_avx512_vnni.onnx` (118.3 MB, sha256 `dd476dd0…48d8`), `onnx/tokenizer.json`, `onnx/tokenizer_config.json`, `onnx/config.json`** (the four sha256 in evidence.md). Why: int8 vs fp32 cosine mean 0.9965, identical top-3, 3.7 ms vs 7.1 ms single, 559 vs 725 MB RSS; e5 beats MiniLM-L12 on the `apteka`/`подарки` probes at identical cost; intfloat carries an explicit MIT licence (the Xenova re-export has no licence field). Runtime: `onnxruntime`, `tokenizers`, `numpy` (126 MB, 4 packages) — NOT `fastembed` (30 packages, pulls requests/loguru/pillow). No torch anywhere. `pyproject`: `onnxruntime>=1.31,<2`, `tokenizers>=0.23,<1`, `numpy>=2,<3`.
- **D-M2 Protocol** (`types.py`, app-free: numpy + stdlib): `class Embedder(Protocol): name: str; model: str; dim: int; def embed(self, texts: Sequence[str], *, kind: Literal["query","passage"]) -> NDArray[float32]` — SYNC, CPU-bound, returns `(n, dim)` L2-normalised rows. The `query: `/`passage: ` prefixes are a property of e5, so `OnnxEmbedder` prepends them; the canonical text (§3) never contains them. Mean pooling over the mask, `token_type_ids` zeros, tokenizer truncation at `max_length=128` (a passage is merchant+note+4 short fields — 128 tokens is generous; 512 would only make the sweep slower).
- **D-M3 Fake** (`fake.py`): deterministic hashed bag-of-words — casefold, split on non-letters, each token hashed into one of 384 buckets (+1), L2-normalise; `kind` ignored; `name="fake"`, `model="fake"`, `dim=384`. A query sharing a word with a passage scores high, so router tests and the CI evals have a meaningful ranking without the artifact. Deliberately NOT an oracle (categorize fake rule).
- **D-M4 Construction vs load.** `registry.embedder_from_settings(settings) -> Embedder | None`: `embeddings_provider ∈ onnx|fake|off`; `onnx` → `OnnxEmbedder(model_dir, threads)` constructed with NO I/O (house rule, every `app.state` seam); `fake` → `FakeEmbedder()`; `off`/unknown → `None` + WARNING. The lifespan then calls `await asyncio.to_thread(embedder.load)` BEFORE the scheduler; `load()` reads `model_manifest.json` (§2), verifies the sha256 of every file in `model_dir`, builds the ORT session (`intra_op_num_threads = inter_op_num_threads = embeddings_threads`, graph opt `all`), warms with one `embed(["warmup"], kind="query")`. Missing dir / hash mismatch / ORT failure → ONE WARNING (file name + reason, never a traceback at boot) and `app.state.embedder = None` — a missing model is "search not available", never a boot failure (the Ollama "unreachable localhost" rule). conftest sets `embeddings_provider="fake"` where it sets the three scheduler gates false; `FakeEmbedder.load()` is a no-op. Tests swap `app.state.embedder` BEFORE the lifespan (the `app.state.llm` precedent) — the lifespan loads whatever object it finds.
- **D-M5 Serialisation + threads.** ONE `threading.Lock` inside `OnnxEmbedder.embed`; every caller goes through `asyncio.to_thread`. `embeddings_threads = 1` on 2 vCPU: one batch may not take both cores from request handling (evidence: 2.45 ms/item at 2 threads on arm64 — re-measure in the amd64 image; at 1 thread a 32-batch is ~150 ms of lock hold, so a search query waits ≤150 ms behind a sweep batch). Batch size `embeddings_batch_size = 32` (per-item cost is flat from 32 to 128, 32 bounds the hold). ORT sessions are thread-safe; the lock is about the box, not correctness.
- **D-M6 Not available on the wire:** 503 `EMBEDDINGS_NOT_AVAILABLE` from a new `ai_gate.require_embedder` (same shape as `require_llm_provider`; distinct string because the cause — a missing artifact — is not the LLM key). The sweep job no-ops with one info line (push_jobs keyless precedent). `EMBEDDINGS_PROVIDER=off` is the prod kill switch if RAM gets tight: search/QA 503, nothing else moves.

## 2. Artifact: build-time fetch (`Dockerfile`, `model_manifest.json`, `scripts/fetch_model.py`)
- **D-A1 One manifest, two readers.** `apps/api/model_manifest.json`: `{"repo","revision","files":{"<hf path>":{"sha256","as":"<local name>"}}}` with the four files of D-M1. `scripts/fetch_model.py` (stdlib only: `urllib`, `hashlib`, `argparse`; run with `python -I`) downloads `https://huggingface.co/<repo>/resolve/<revision>/<path>` into `--dest`, streams to a temp file, verifies sha256, renames to `as`, exits non-zero on ANY mismatch; skips a file already present with the right hash (idempotent). `OnnxEmbedder.load` reads the SAME manifest to verify at boot — one source of truth for the pins.
- **D-A2 Dockerfile stage** `FROM python:3.12-slim-bookworm AS model` → `COPY model_manifest.json scripts/fetch_model.py ./` → `RUN python -I fetch_model.py --manifest model_manifest.json --dest /models/multilingual-e5-small`; runtime: `COPY --from=model --chown=app:app /models /app/models`. The layer is keyed by the manifest bytes, so a rebuild without a pin change never re-downloads; the image grows ≈ +240 MB (artifact + wheels, evidence). No HF token, no `huggingface_hub`.
- **D-A3 Dev.** Default `embeddings_model_dir = "models/multilingual-e5-small"` (relative to cwd: `/app/models/…` in the image, `apps/api/models/…` on the host — one default, both stands). Host run: one-off `uv run python -I scripts/fetch_model.py --manifest model_manifest.json --dest models/multilingual-e5-small` (`apps/api/models/` gitignored), or `EMBEDDINGS_PROVIDER=fake` in `apps/api/.env`. `docker-compose.yml` needs NO edit (the api build context already is `apps/api`; the stage runs inside it). `docs/infra.md` gets both lines.
- **D-A4 Prod deploy** = the ordinary `deploy/update.sh` (rebuild + recreate); backup first by habit, but no DB image swap and no data step (§4). Re-measure RSS in the running container and record it in `docs/deploy.md` (ceiling note: API ≈ 700 MB expected).

## 3. Canonical text (`services/tx_text.py`, pure; `domain/country_names.py`)
- **D-T1 Template** `TEXT_VERSION = "tx-text-v1"`; parts in this order, empty ones omitted, joined by ` | `: `merchant`, `note` (collapsed whitespace, cut to 300 chars), `category name`, kind word (`expense`/`income`, English — the model is multilingual and the probe queries were RU/PL/EN against EN fields), `"<English name> (<CODE>)"` for `country` (evidence: name beside code wins every probe; code alone is borderline), `account name`. NO amounts (numbers match lexically, not semantically — a `500` in text pulls every query containing a figure; the total is the server's), NO dates (filters). Pinned by a test over one full row and one merchant-only row.
- **D-T2 Country names:** `domain/country_names.py` — a frozen dict of the 249 ISO-3166-1 alpha-2 codes → English short names (generated once, committed; stdlib only; a test pins the count and `PL`/`BY`/`DE`). Unknown code → `"(<CODE>)"` only. The first server-side name table; the web keeps `Intl.DisplayNames`.
- **D-T3 Hash** `text_hash = sha256(TEXT_VERSION + "\n" + text)` hex. Any template edit bumps `TEXT_VERSION` → every stored hash mismatches → the sweep re-embeds the world. That IS the reindex path; no CLI.
- **D-T4 Population = `_NOT_TRANSFER_OR_DEBT`** (`kind IN (expense, income) AND debt_id IS NULL`), the exact rows every money aggregate sees. Transfers and debt movements are NOT indexed: their text is two account names / a counterparty that lives on the debt, and indexing them would force the total to carry a third "excluded" counter. Searchable ⇔ totalable, one population; `?kind=transfer` on search answers an honest empty list. Revisit trigger: a real question about transfers.

## 4. Storage — **D-S1 plain BYTEA + in-process numpy, NO pgvector**
Evidence: cosine + top-20 over 20 000 rows = 0.56 ms, 30 MB transient; 5 000 rows = 0.09 ms; the owner's ledger is low thousands. pgvector would cost an image swap in three places (dev compose the owner applies, prod recreate, CI service), +140 MB Debian image, `CREATE EXTENSION`, a deploy step — for no measurable benefit at ≤ 20 k rows/user. `vector` = 384 × float32 little-endian (1536 bytes, `np.frombuffer`), CHECK `octet_length(vector) = 1536`. Per-search scan is bounded by `search_max_candidates = 20_000` (newest first; the response says `candidates`). Follow-up trigger recorded as `rag-pgvector`: > 50 k indexed rows for one user or search p95 > 50 ms.

## 5. Indexing — **D-I1 PULL, not push hooks**
- Push would mean an after-commit hook in SEVEN writers (POST/PATCH/DELETE `/transactions`, `apply.py` create+delete, `recurring_jobs`, `debt_writes` + `/debts` PATCH/DELETE, `/debts/{id}` cascade, user cascade) PLUS category and account renames (names are in the text) PLUS psql — and every hook is a place a write can slow or fail. Pull: `transaction_embeddings(transaction_id PK FK ON DELETE CASCADE, user_id, model, text_hash, vector, embedded_at)`; a row is CURRENT iff it exists with `model == embedder.model` and `text_hash == hash(text now)`. Deleted rows vanish by cascade; renamed categories/accounts and edited rows become stale by hash; writers stay byte-identical; a write never embeds.
- **D-I2 Stale detection** (`services/tx_index.py`): ONE query per user — indexed population columns (`merchant, note, category name, kind, country, account name`) LEFT JOIN embeddings (`model, text_hash`) — hash in Python, compare. At 5 k rows that is one SELECT + 5 k sha256 ≈ tens of ms. (No `updated_at` on `transactions`; adding one would be a push-shaped change. Revisit if the scan shows in a profile.)
- **D-I3 Three repair paths, one function** `refresh(session, embedder, user_id, *, max_rows) -> RefreshStats(embedded, pending)`: embed stale rows in `embeddings_batch_size` batches via `asyncio.to_thread`, upsert `INSERT … ON CONFLICT (transaction_id) DO UPDATE SET model, text_hash, vector, embedded_at`, commit per batch (a crash loses a batch, never the table). A row deleted between read and upsert → the batch's FK error rolls back THAT batch, logged, retried by the next run. (a) **Scheduler sweep** `EMBEDDINGS_SCHEDULER_ENABLED` (gated like the three; conftest false), `IntervalTrigger(minutes=embeddings_sweep_interval_minutes=5)`, `coalesce=True, max_instances=1`; per run `refresh` per user with stale rows (users found by one SQL over missing/model-mismatch rows, then the hash pass), hard cap `embeddings_sweep_max_rows = 2000`, `asyncio.timeout(embeddings_sweep_time_budget_seconds = 120)`. (b) **Boot run-now job** (the recurring D5 precedent) = the backfill on first deploy and after a `TEXT_VERSION`/model change. (c) **Search-time refresh** bounded at `search_max_refresh = 64` rows for THIS user (≤ 64 × ~5 ms, keeps "I just added it, now search" true for the common case); the response carries `pending_count` = stale rows still not embedded, so a 1 000-row import right before a search is honest rather than silently missing.
- **D-I4 Never fails or slows a write** by construction (no hook); the sweep never raises out of the job (the materialize_due contract), logs ONE line per run: `embeddings sweep users=… embedded=… pending=… ms=…` — no text, no ids.

## 6. Retrieval (`services/tx_search.py` → `routers/tx_search.py`)
- **D-R1 Router placement.** A NEW router `routers/tx_search.py` mounted at prefix `/transactions` BEFORE `transactions.router` with `dependencies=[Depends(prime_rate_limit)]` — the `goal_items` precedent: it owns the static segment `/search` so `/{transaction_id}` can never shadow it, and the existing transactions router keeps its "never calls limiter.limit" mount comment intact. Rate limit `search_rate_limit = "30/minute"` per user via `user_rl_key("search")`; the stash dependency is a 3-line local `_stash_rl_user` over `current_user_jwt_or_pat` (the shared `stash_rl_user` is JWT-only, and `rate_limit` importing `pat_auth` would cycle). PAT callers additionally pay the per-token read limit — defence in depth, not a bug.
- **D-R2 `GET /transactions/search`** query: `q` (required, `max_length=500`; stripped; blank → 422 `SEARCH_QUERY_BLANK`), `k` (default 20, 1..50), `from`/`to`/`category_id`/`kind`/`account_id`/`country` (the `read_filters` subset without `q`/`goal_item_id`/`sort` — the same function, so the filter semantics cannot drift), `min_score: float | None` (0..1, absolute cosine, default none). Gate order: auth → `require_embedder` 503 → limiter → session. Steps: filters → stale refresh (D-I3c) → `SELECT id, vector FROM embeddings JOIN transactions WHERE <filters> AND model = current ORDER BY occurred_at DESC LIMIT search_max_candidates` → query embedding → `scores = M @ q` → top-k (ties by `occurred_at desc, id`) → `min_score` cut → load the k rows → `serialize_transaction` → total.
- **D-R3 Score semantics:** raw cosine, 4 dp, returned as `score`; NO server-side relative cut-off in v1 (evidence: everything sits in 0.78–0.87 and correct-vs-wrong margins are 0.006–0.03 — any default would drop true hits; `k` bounds the set). The evals report gold-vs-non-gold score distributions; a calibrated default `min_score` is an additive follow-up. The tool description tells the model scores are RELATIVE.
- **D-R4 Total = `tx_totals.converted_total_for_rows(session, rows, base) -> RowsTotal(income_minor, expense_minor, unconverted_count)`** — a NEW function in `tx_totals.py`, the same three buckets in the same arm order (`currency == base` → amount; `base_currency == base` → snapshot; else `lookup_rate` + `convert_minor`, miss → `unconverted_count`), a Python fold over an explicit row list (≤ 50). Lives in `tx_totals` so the bucket order is written once; no new money math. `net_minor = income − expense`. Base from `read_base_currency`.
- **D-R5 Projection:** `TransactionSearchRead {items: [TransactionSearchHit {transaction: TransactionRead, score: float}], total: {currency, income_minor, expense_minor, net_minor, unconverted_count}, pending_count: int, candidates: int, model: str}`. Embed `TransactionRead` rather than a lean DTO: the web's row renderer, `rowDisplay.primaryAmount` and MCP all consume exactly that shape, and a second money projection would be a second opinion on which amount leads. `TransactionRead` itself is byte-identical (hit wraps, never extends).
- **D-R6 Hybrid with `?q=` ILIKE: not in v1.** Follow-up `rag-hybrid` (RRF over ILIKE + cosine), gated on the retrieval evals showing exact-merchant queries losing to paraphrases. `list_transactions?q=` stays the exact-text tool; the two tool descriptions say which is which.
- **D-R7 MCP:** `@mcp_tool(name="search_transactions", description=…, params={q, k, from, to, category_id, kind, account_id, country, min_score})` on the GET — read ⇔ GET, present in stdio AND the remote connector by construction. `READ_TOOLS` grows by one at the walk position (mounted before `transactions.router` → right after `get_debt`, before `list_transactions`); `mcp_tools_snapshot.json` +1 (41). Description states: by meaning, scores relative, use `total` instead of adding rows, `pending_count > 0` means recent rows are not yet searchable.

## 7. Q&A (`services/advisor_qa.py` pure → `routers/advisor_qa.py`)
- **D-Q1 Shape:** `POST /advisor/qa` body `AdvisorQaAsk {question (AdvisorAsk's caps and blank rule), k = 20 (1..50), from, to, account_id, kind}` → `AdvisorQaRead {answer: str | null, citations: [TransactionSearchHit], dropped_citations: int, retrieved_count: int, total: <§6 total>, provider, model, prompt_version}`. JWT-only (`current_active_user` via `stash_rl_user`; AI spend, the `/advisor/ask` rule), `# MCP: no — in MCP the client model IS the answerer; it has search_transactions`. Gate order: auth → `require_llm_provider` (503 `AI_NOT_CONFIGURED`) → `require_embedder` (503 `EMBEDDINGS_NOT_AVAILABLE`) → `advisor_qa_rate_limit = "5/minute;30/day"` (`user_rl_key("advisor-qa")`) → session. New router module (advisor.py is the Anthropic-streaming seam; mixing two seams in one file is the thing ai-layer avoided), mounted at `/advisor` with `prime_rate_limit`; `/qa` vs `/ask` — no static-segment conflict.
- **D-Q2 Not streamed, no history.** One `structured()` call: the citations are verified against the whole answer, which does not exist until the call ends; a stream would have to withhold citations or emit unverified ones. History: none in v1 — each question re-retrieves; a follow-up (`rag-qa-history`) must first decide whether a turn re-retrieves or reuses the previous set.
- **D-Q3 Retrieval reuse:** the router calls `tx_search.search(...)` with the body's filters (same function as the GET — one definition of "what was retrieved"). Zero hits → NO LLM call, `answer: null`, `citations: []` (the server writes no prose; the web renders its own "nothing found" copy).
- **D-Q4 Prompt `PROMPT_VERSION = "qa-v1"`**, fingerprint pinned (the categorize pattern). System: answer in `language` (profile.language, passed in the document — the reconcile rule), plain text, use ONLY the listed operations, cite by key every operation the answer relies on, the total is given and is the only sum you may state, no arithmetic on amounts. User = ONE JSON document `{"qa": {"question", "language", "base_currency", "total": {income, expense, net, unconverted_count}, "operations": [{"key": "o1", "date", "kind", "amount", "currency", "merchant", "note", "category", "country", "account", "score"}]}}` — amounts as major-unit strings (`to_major_string`), keys `o1..ok` in rank order. Schema `{answer: string, citations: array of enum(o*)}`, `additionalProperties: false`. `max_tokens = 1024`.
- **D-Q5 Verification (server, never trusted):** parse → `citations` must be strings; unknown key / duplicate → DROPPED and counted in `dropped_citations`; order of first appearance kept; keys → ids → the hits of the retrieved set. `answer` stripped, cut to 4000 chars; empty → `invalid_output`. Errors: `unavailable`/`request_rejected` → 503 `AI_UNAVAILABLE`; `invalid_output`/`truncated`/`unsupported` → 422 `QA_FAILED` (the pdf-reconcile mapping). `log_call(prompt_version="qa-v1", batch_size=k, user_id=…)` per call.
- **D-Q6 Fake arm** (`llm/fake.py`, 4th document key `qa`): cites every operation whose `merchant`/`note`/`category` shares a casefolded word with the question; answer = `"scripted fake answer: " + ", ".join(cited keys)` (or `"no match"`); the marker `QA_CITE_FOREIGN` in the question APPENDS citation `"o999"` — a key no document carries — so the verifier's drop arm is testable on a QA stand and in the suite; `LLMFAIL` → `unavailable` (existing scan).

## 8. Database — `0020_transaction_embeddings.py`
### Tables
- `transaction_embeddings`: `transaction_id` Uuid PK, FK `transactions.id` ON DELETE CASCADE; `user_id` Uuid NOT NULL FK `users.id` ON DELETE CASCADE (denormalised: the per-user scan must not join to filter); `model` String(64) NOT NULL; `text_hash` String(64) NOT NULL; `vector` BYTEA NOT NULL; `embedded_at` DateTime(tz) NOT NULL server_default `now()`. CHECKs (hand-written, byte-identical in model and migration — the 0018/0019 rule, pinned by `test_core_model`): `vector_dim` = `octet_length(vector) = 1536`; `text_hash_format` = `text_hash ~ '^[0-9a-f]{64}$'`; `model_present` = `model <> ''`. Index `ix_transaction_embeddings_user_id` (the scan); the PK serves the upsert. No enum (the model id is a stamp, not a closed set).
### Migration steps
1. `create_table` + three CHECKs + index. 2. No backfill — the boot sweep is the backfill. 3. Downgrade: `drop_table`. Nothing else in the schema changes; `transactions` is untouched.

Dependency direction: routers → services → (embeddings | llm | domain | models). `embeddings/` imports numpy/onnxruntime/tokenizers/`config`/stdlib — app-free so `evals/retrieval.py` drives it with no app. `tx_text.py`, `country_names.py`, `advisor_qa.py` never import `models`/`db`/`fastapi`/the limiter; `tx_index.py`/`tx_search.py` own the DB like `tx_totals.py`. Contract: `openapi.json` + `schema.d.ts` in one commit (two new routes, four new schemas, three new codes on the `anyOf`s: `SEARCH_QUERY_BLANK`, `QA_FAILED`, `EMBEDDINGS_NOT_AVAILABLE`). Web contract named for the frontend plan: `GET /transactions/search` (key `['transactions','search',{q,filters,k}]` — the existing tx-write predicate `key[1] !== 'summary'` already invalidates it) and `POST /advisor/qa` (citations → `/transactions?…` links or the row modal by `transaction.id`); copy for the two 503s and `pending_count`.

## 10. Evals (`apps/api/evals/`)
- **D-E1 Retrieval dataset** `dataset/retrieval-v1/{corpus,queries}.jsonl`, GENERATED by `gen_retrieval.py --seed` (themed merchant lists RU/PL/EN — car, pharmacy, groceries, gifts, Poland/Germany/Belarus — with note/category/country/account; queries in three languages with gold key sets) PLUS `--derive-owner`: from `owner-categorize-v1.jsonl`, one query per label with ≥ 3 rows (`query = label`, `gold = rows of that label`, fields `text→merchant, kind, country`) — 22 labels, real anonymised merchants, zero new PII. Metrics: recall@5/10/20, MRR, per-language recall, gold-vs-non-gold cosine percentiles (for D-R3). The corpus is embedded through `tx_text` + the embedder directly (no DB, no app); the runner takes `--embedder fake|onnx --model-dir`.
- **D-E2 What CI runs: the FAKE embedder.** The real artifact is 135 MB from Hugging Face; a pinned-and-cached CI download is possible but adds a third-party outage mode to every API push. Real numbers are produced LOCALLY (`--embedder onnx`), the report committed as `reports/retrieval-onnx-<model>-tx-text-v1.{md,json}` with `real: true`, the manifest revision and sha256 inside; the fake report says `synthetic: true` in its first lines (`synthetic_banner`). `tests/test_evals_regression.py` replays the fake run with `RETRIEVAL_MIN_RECALL_AT_10` calibrated a hair below the fake (word-overlap queries only). Opt-in later: a `workflow_dispatch` job with `actions/cache` keyed by the manifest — recorded, not built.
- **D-E3 Groundedness** `evals/qa.py`: fake embedder → `tx_search`-free in-memory retrieval over the corpus → `advisor_qa.answer_question` via the LLM replay store (`replay/<provider>-<model>-qa-v1.jsonl`); measures raw model groundedness = `dropped_citations / citations_before_drop` (post-verifier ⊆ holds by construction — the number that matters is how often the model had to be corrected), citation recall vs `gold ∩ retrieved`, cost/latency. Replayed in CI with the fake LLM; a real `--mode record` run lands labelled.

## Test seams
1. `embeddings`: `FakeEmbedder` determinism + normalisation; `OnnxEmbedder.load` with a wrong hash → `None` path (a 3-byte fixture file, no artifact); `tx_text` template + hash pin; `country_names` count.

## Trade-offs considered
- **Pull vs push indexing:** pull (D-I1) — zero writer changes, renames covered for free, a write can never be slowed or failed by the model; cost = a bounded search-time refresh and `pending_count` honesty. Push would be seven hooks plus two rename hooks and still miss psql.
- **In-process numpy vs pgvector:** numpy (D-S1) — 0.6 ms at 20 k rows, no image swap; pgvector is the recorded follow-up with a numeric trigger.
- **Index transfers/debts (excluded from the total) vs not index them:** not indexed (D-T4) — one population for search and money, no third counter.
- **Lifespan load vs lazy first-request load:** lifespan — a 0.3 s / 510 MB step belongs at boot where `/health` and the operator see it, not in the first user's request.
- **Fake embedder as hashed bag-of-words vs random vectors:** bag-of-words — random vectors make every ranking test vacuous.
- **Q&A as `structured()` vs streaming text with post-hoc citation parsing:** structured (D-Q2) — the schema enum plus the server check beat regex-mining citations out of prose.
- **New routers vs extending `transactions.py`/`advisor.py`:** new (D-R1/D-Q1) — the static-segment landmine and the rate-limit mount contract both argue for it; the existing routers stay byte-identical.
- **CI with the real model vs fake:** fake (D-E2) — a hosted-artifact dependency in CI buys a number the owner can produce locally for free.

## What this does NOT decide
- Exact `qa-v1` prompt wording; the tool description prose for `search_transactions`; the `gen_retrieval` theme lists and sizes; the fake-calibrated floors.
- `FakeEmbedder`'s hash function and `OnnxEmbedder`'s pooling code details (bounded by D-M2's contract: L2-normalised `(n, 384)`).
- Whether the sweep's hash pass needs an SQL pre-filter at real volumes (D-I2 revisit), and the defaults in §9 — starting points; the first prod RSS measurement may lower `search_max_candidates` or switch `embeddings_threads`.
- Web UI: the "by meaning" mode toggle, result rendering with scores, the Q&A section and citation links, ru/en copy — frontend plan over the contract named above. Mobile stays frozen.
- Follow-ups recorded, not designed: `rag-hybrid` (D-R6), `rag-pgvector` (D-S1), `rag-qa-history` (D-Q2), `embeddings-vocab-prune` (evidence: −350 MB with a self-made artifact), opt-in real-model CI job (D-E2).
