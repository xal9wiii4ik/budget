# Приложение для бюджета — план и архитектура (бэкенд на Python)

Личный трекер бюджета: мобильное приложение (iOS/Android) на Expo, веб — отдельное React-приложение, бэкенд на FastAPI, база Postgres. Общий у клиентов не UI, а всё под ним: сгенерированный API-клиент, типы и утилиты в shared-пакетах. Приложение делается для себя, поэтому приоритет — скорость разработки и простота, но без решений, которые придётся ломать при росте.

## Фичи и как они реализованы

### Вход в приложение

Сейчас — только email + пароль. Регистрация `POST /auth/register`, вход `POST /auth/login`, сервер выдаёт пару access-токен (JWT, живёт ~15 минут) и refresh-токен (живёт ~30 дней, хранится в базе и отзывается). Пароли — только хэши (argon2 через библиотеку `pwdlib`). Реализация на `fastapi-users` — она сразу даёт регистрацию, вход, refresh и сброс пароля.

Задел на будущее: `fastapi-users` из коробки поддерживает OAuth (Google, Apple) — добавление соцсетей позже сведётся к регистрации OAuth-клиента и паре строк конфигурации, схема базы уже это учитывает (таблица `oauth_accounts` связана с тем же пользователем, аккаунты склеиваются по email). Клиент про способ входа ничего не знает — он просто получает JWT, поэтому фронт переделывать не придётся.

### Добавление траты по фото чека

Полный путь картинки от камеры до транзакции:

1. Пользователь фотографирует чек или выбирает файл из галереи (`expo-image-picker`); клиент сжимает картинку до ~1500px по длинной стороне (`expo-image-manipulator`) — этого хватает для распознавания, а трафик и хранилище экономятся в разы.
2. Клиент вызывает `POST /receipts` — сервер создаёт запись со статусом `pending` и возвращает presigned URL для загрузки в хранилище (S3-совместимое, файл лежит по пути `{user_id}/{uuid}.jpg` в приватном bucket).
3. Клиент грузит файл напрямую по этому URL (файл не проходит через API — не занимает воркеры) и дёргает `POST /receipts/{id}/parse`.
4. Фоновая задача (FastAPI `BackgroundTasks`) скачивает файл, отправляет в Claude API с промптом «верни строго JSON: {total, currency, merchant, date, items[], suggested_category_id}» и списком категорий пользователя; ответ валидируется Pydantic-схемой. Успех → `parsed_json` + статус `parsed`, ошибка → статус `failed` с причиной.
5. Клиент опрашивает `GET /receipts/{id}` раз в пару секунд и, когда чек распознан, показывает предзаполненную форму транзакции: сумма, дата, магазин, предложенная категория.
6. Пользователь подтверждает или правит — только после этого создаётся запись в `transactions` со ссылкой на чек. Молчаливая автозапись запрещена: OCR ошибается, и одна неверная сумма без подтверждения подрывает доверие ко всей статистике.

Тот же механизм работает для скриншотов оплат и банковских пушей — промпт не привязан к формату бумажного чека.

### Категории

Два уровня: системные (общий стартовый набор — продукты, транспорт, жильё, здоровье и т.д., `user_id = null`) и пользовательские. Пользователь может создавать свои, переименовывать, задавать иконку/цвет, архивировать (не удалять — на категорию ссылаются старые транзакции). У категории есть тип: расход или доход.

Назначение категории трате происходит тремя путями: вручную при вводе; автоматически при распознавании чека (Claude выбирает из списка категорий пользователя); и автоподсказкой по мерчанту — сервер запоминает пары «мерчант → категория» из прошлых подтверждённых транзакций и при повторе того же мерчанта подставляет категорию сам. Приоритет у ручного выбора: если пользователь исправил категорию, эта пара запоминается и перекрывает старую.

### Цели накоплений

Пользователь создаёт цель: название, сумма, валюта, дедлайн (опционально). Приложение считает `monthly_needed = (target − saved) / months_left` и сравнивает с реальным свободным остатком — `средний доход − средние расходы за последние 3 месяца` из фактических транзакций, а не из обещаний. Если откладывать нужно больше, чем реально остаётся, приложение говорит это прямо и предлагает: сдвинуть дедлайн (обратный расчёт `months = (target − saved) / available`), уменьшить сумму или показывает категории, урезание которых закрывает разрыв. Пополнения цели фиксируются отдельными записями (`goal_contributions`) — виден прогресс по месяцам. При нескольких целях свободный остаток делится по приоритетам, которые расставляет пользователь.

Вся математика — чистые функции в `domain/goals.py`, покрытые юнит-тестами.

### Мультивалютность

Каждая трата хранится в своей валюте как есть: `amount_minor` (целое число в копейках/центах, никогда float) + код валюты. У пользователя есть базовая валюта; все сводки и графики конвертируются в неё по курсу на дату операции. Курсы тянутся раз в сутки планировщиком из внешнего API (frankfurter.app / exchangerate.host / ЦБ) и кэшируются в таблице `exchange_rates` — конвертация не зависит от доступности внешнего API. Смена базовой валюты меняет только отображение, исходные данные не пересчитываются. Валюта транзакции определяется автоматически из чека, иначе подставляется базовая.

### Статистика

Готовые срезы: расходы по категориям за период (месяц/квартал/год/произвольный), динамика по месяцам, сравнение с прошлым периодом, доходы vs расходы, топ-мерчанты, прогресс целей. Всё считается SQL-агрегатами на лету по индексу `(user_id, occurred_at)` — на личных объёмах это миллисекунды. API отдаёт готовые к отрисовке ряды, клиент рисует их в Victory Native XL и ничего не пересчитывает.

### AI-советник

Чат внутри приложения: «куда уходят деньги», «где можно сэкономить», «успею ли накопить к августу». Эндпоинт `POST /advisor/ask` собирает компактную сводку (агрегаты за 3 месяца, цели, доход — сырые транзакции в промпт не попадают), передаёт Claude и стримит ответ через SSE. На AI-эндпоинтах стоит дневной лимит запросов — защита собственного кошелька от счёта за API.

## 1. Стек

**Мобильный клиент — Expo (React Native) с expo-router.** Нативные iOS/Android приложения. Камера через `expo-image-picker`, графики через Victory Native XL, состояние — TanStack Query + Zustand.

**Веб-клиент — React (Vite + TypeScript).** Обычное SPA: React Router, TanStack Query + Zustand (те же паттерны, что на мобиле), графики — Recharts, загрузка чеков через input/drag-and-drop. Приложение живёт за логином, поэтому SSR и SEO не нужны — Vite проще и быстрее Next.js; статика деплоится на Vercel/Netlify/Cloudflare Pages. Оба клиента — на React и TypeScript, так что мышление, хуки и слой данных переиспользуются, различается только слой разметки.

**Бэкенд — FastAPI (Python 3.12).** Pydantic v2 для схем, SQLAlchemy 2.0 (async) + Alembic для базы и миграций, `fastapi-users` для авторизации, httpx для внешних API, официальный SDK `anthropic` для Claude. Ежедневные задачи — APScheduler. Деплой — Docker-контейнер на Railway, Fly.io или Render; OpenAPI/Swagger-документация из коробки.

**База — управляемый Postgres** (Neon, Railway, Supabase-как-просто-база — любой, это обычный Postgres).

**Файлы — S3-совместимое хранилище** (Cloudflare R2 — бесплатный лимит щедрый, или MinIO при self-host). Приватный bucket, доступ по presigned URL с коротким TTL.

### Компромиссы, которые стоит понимать

*Свой auth vs Supabase Auth.* Раз вход пока только по паролю и приложение личное, `fastapi-users` проще: одна система, никакой внешней зависимости, а OAuth добавляется в него же позже. Supabase Auth стал бы выгоден, если бы соцсети нужны были с первого дня.

*FastAPI vs Django.* Django даёт админку и батарейки, но тянет синхронную идеологию и лишний вес для чистого JSON-API под мобильный клиент. FastAPI легче и естественнее для async-вызовов внешних API. Захочется админку — добавляется `sqladmin` поверх тех же моделей.

*Два клиента vs Expo universal.* Отдельный React-веб означает, что каждый экран делается дважды — это цена за нормальный веб-интерфейс: полноценные таблицы, drag-and-drop, привычные веб-паттерны вместо «растянутого мобильного» вида react-native-web. Цена снижается общими пакетами: API-клиент, типы, форматирование денег и дат, валидация пишутся один раз. Начинать можно с одного клиента (например, веба — итерации быстрее), а мобильный догонит по готовому API.

*Vite vs Next.js для веба.* Next.js даёт SSR и SEO, которые приложению за логином не нужны, но добавляет серверный рантайм и усложняет деплой. Vite — просто статика. Если позже появится публичная часть (лендинг, шаринг отчётов) — это отдельный сайт или точечный переезд.

## 2. Модель данных

Все суммы — целые числа в минорных единицах. Для курсов — `Decimal`, никогда `float`.

| Таблица | Ключевые поля | Назначение |
|---|---|---|
| `users` | id, email, hashed_password, is_active | Пользователи (`fastapi-users`) |
| `oauth_accounts` | id, user_id, provider, account_id | Задел под вход через соцсети |
| `profiles` | user_id, base_currency, monthly_income_minor | Настройки |
| `categories` | id, user_id (null = системная), name, icon, kind, archived | Категории |
| `merchant_category_map` | user_id, merchant, category_id | Память автокатегоризации |
| `transactions` | id, user_id, amount_minor, currency, category_id, occurred_at, note, receipt_id | Операции |
| `receipts` | id, user_id, storage_path, status, parsed_json, error | Чеки |
| `goals` | id, user_id, name, target_minor, currency, saved_minor, deadline, priority | Цели |
| `goal_contributions` | id, goal_id, amount_minor, occurred_at | Пополнения целей |
| `exchange_rates` | base, quote, rate, as_of_date | Кэш курсов |

Модель ядра на SQLAlchemy:

```python
class Transaction(Base):
    __tablename__ = "transactions"

    id: Mapped[uuid.UUID] = mapped_column(primary_key=True, default=uuid.uuid4)
    user_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("users.id"), index=True)
    amount_minor: Mapped[int] = mapped_column(BigInteger)
    currency: Mapped[str] = mapped_column(String(3))
    category_id: Mapped[uuid.UUID | None] = mapped_column(ForeignKey("categories.id"))
    occurred_at: Mapped[date]
    note: Mapped[str | None]
    receipt_id: Mapped[uuid.UUID | None] = mapped_column(ForeignKey("receipts.id"))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

    __table_args__ = (Index("ix_tx_user_date", "user_id", "occurred_at"),)
```

## 3. Безопасность

Каждый защищённый эндпоинт получает текущего пользователя через общую зависимость (`Depends(current_active_user)`) и фильтрует все запросы к базе по его id — проверку невозможно «забыть». Секретные ключи (Claude, валютный API, строка подключения к БД, JWT-секрет) — только в env сервера. Rate-limit на AI-эндпоинты через slowapi. Фото — в приватном bucket, только presigned URL с коротким TTL. CORS — только домены приложения. Пароли — argon2. Даже для личного приложения это не перебор: API торчит в интернет.

## 4. Структура проекта

Монорепо (pnpm workspaces + Turborepo): `apps/mobile` (Expo), `apps/web` (React + Vite), `apps/api` (FastAPI), `packages/api-client` (сгенерированный из OpenAPI типизированный клиент — единственный способ ходить в API для обоих фронтов), `packages/shared` (форматирование денег/дат, константы, список валют, zod-схемы форм). Внутри API слои: `routers/` (HTTP), `domain/` (чистая логика: цели, конвертация), `services/` (Claude, курсы, storage), `models/` (SQLAlchemy), `schemas/` (Pydantic). Контракт фронт↔бэк — генерация TypeScript-клиента из OpenAPI-схемы (`openapi-typescript`): типы на клиенте всегда совпадают с сервером.

## 5. Дорожная карта

**Этап 1 — MVP (2–3 недели).** Регистрация/вход по паролю, CRUD транзакций и категорий, одна валюта, список и сводка за месяц. Сначала веб-клиент (итерации быстрее, API обкатывается на нём), деплой API в Docker, веб на Vercel/Netlify. Мобильный клиент подключается к готовому API следом (сборка через EAS в TestFlight/Internal Testing).

**Этап 2 — чеки и AI (1–2 недели).** Хранилище, распознавание чеков, форма подтверждения, автокатегоризация по мерчантам.

**Этап 3 — валюты и цели (1–2 недели).** Курсы + планировщик, конвертация в агрегатах, цели с калькулятором и проверкой реалистичности.

**Этап 4 — статистика и советник (1–2 недели).** Графики, чат-советник со стримингом, экспорт CSV.

**Этап 5 — полировка.** Вход через Google/Apple, push-напоминания, повторяющиеся операции, лимиты по категориям, офлайн-режим.

## 6. Что пересмотреть при росте

Фоновые задачи перерастут `BackgroundTasks` — переехать на arq (async, Redis) или Celery. Понадобится синхронизация между устройствами в реальном времени — WebSocket. Офлайн-режим — локальный SQLite (expo-sqlite) с очередью синхронизации; заметное усложнение, не для MVP. Появятся другие пользователи — добавить подтверждение email и, возможно, вернуться к managed-auth.
